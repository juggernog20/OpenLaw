# MCP and tool register — research notes

These notes collect what the primary sources say about exposing a self-hosted product as an MCP server, and about the "tool register" (which tools exist, how they are grouped, and who may call them). They feed a grill session on the inbound agent surface for OpenLaw. Every claim links to the source it came from. All sources were read on 2026-09-23 unless a note says otherwise. Where a source did not answer a question, the text says "unverified".

## 1. MCP protocol, current state

The current specification revision is `2026-07-28`. The changelog for that revision lists the changes since `2025-11-25` ([changelog](https://modelcontextprotocol.io/specification/latest/changelog)). It is a large break with the earlier revisions.

What changed in `2026-07-28`, in the order the changelog gives it:

- Protocol-level sessions and the `Mcp-Session-Id` header are gone. List endpoints no longer vary per connection. Servers that need cross-call state mint explicit handles and take them back as ordinary tool arguments ([changelog, major change 1](https://modelcontextprotocol.io/specification/latest/changelog)).
- The `initialize` handshake is gone. Every request carries its protocol version and client capabilities in `_meta` (`io.modelcontextprotocol/protocolVersion`, `io.modelcontextprotocol/clientCapabilities`). Clients SHOULD send `io.modelcontextprotocol/clientInfo` on each request; servers SHOULD return `io.modelcontextprotocol/serverInfo` in each result ([changelog, major change 2](https://modelcontextprotocol.io/specification/latest/changelog)).
- Servers MUST implement `server/discover`, which advertises supported versions, capabilities, and identity ([changelog, major change 3](https://modelcontextprotocol.io/specification/latest/changelog)).
- The HTTP GET stream and `resources/subscribe` are replaced by `subscriptions/listen`, one long-lived POST response stream for opted-in change notifications ([changelog, major change 4](https://modelcontextprotocol.io/specification/latest/changelog)).
- Server-initiated requests (`elicitation/create`, `sampling/createMessage`, `roots/list`) are replaced by the Multi Round-Trip Requests pattern. The server returns `resultType: "input_required"` with `inputRequests`; the client retries the original request with `inputResponses` ([changelog, major change 7](https://modelcontextprotocol.io/specification/latest/changelog); [MRTR page](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)).
- Every result carries a required `resultType`, `"complete"` or `"input_required"` ([changelog, major change 8](https://modelcontextprotocol.io/specification/latest/changelog)).
- SSE resumability (`Last-Event-ID`) is removed. A broken stream loses the in-flight request and the client re-issues it ([changelog, major change 9](https://modelcontextprotocol.io/specification/latest/changelog)).
- Tasks moved out of core into the `io.modelcontextprotocol/tasks` extension ([changelog, major change 6](https://modelcontextprotocol.io/specification/latest/changelog)).
- Roots, Sampling, and Logging are deprecated. Dynamic Client Registration (RFC 7591) is deprecated in favour of Client ID Metadata Documents ([changelog, deprecated 1 and 4](https://modelcontextprotocol.io/specification/latest/changelog)).

Transports. The spec defines two bindings: stdio and Streamable HTTP ([transports overview](https://modelcontextprotocol.io/specification/latest/basic/transports)). Under Streamable HTTP the server exposes one endpoint that accepts POST. Each JSON-RPC request is its own POST. The server answers with either a single JSON object or an SSE stream scoped to that request. Every POST MUST carry `MCP-Protocol-Version`, `Mcp-Method`, and (for `tools/call`, `resources/read`, `prompts/get`) `Mcp-Name` headers that mirror the body; a mismatch is a `400` with error `-32020` `HeaderMismatch`. Servers MUST validate the `Origin` header and SHOULD bind to localhost when running locally. GET and DELETE on the endpoint get `405` from a modern-only server ([Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)). The 2024-11-05 HTTP+SSE transport has been deprecated since `2025-03-26` and is now formally Deprecated under the feature lifecycle policy; new implementations SHOULD NOT adopt it ([Streamable HTTP, HTTP+SSE section](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)).

Backward compatibility. The spec names two eras: "modern" (`2026-07-28` and later, per-request metadata) and "legacy" (`2025-11-25` and earlier, `initialize` handshake). A server MAY serve both eras on one endpoint. A legacy client against a modern-only server fails with no fall-forward path. A dual-era server answers `initialize` with legacy semantics and modern `_meta` requests statelessly ([versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)). This matters because the SDK notes below show the mainstream clients were still on the legacy era when the SDK v2 shipped.

Tools. A tool has `name`, optional `title`, `description`, `inputSchema` (JSON Schema, 2020-12 by default), optional `outputSchema`, optional `icons`, and optional `annotations`. Tool results carry `content` blocks, optional `structuredContent`, and `isError`. Servers that declare `tools.listChanged` SHOULD send `notifications/tools/list_changed` to clients that opened a `subscriptions/listen` stream with `toolsListChanged: true`. `tools/list` supports cursor pagination and now carries `ttlMs` and `cacheScope` caching hints. Servers SHOULD return tools in a deterministic order for prompt-cache hits. The tool set MUST NOT vary per connection but MAY vary by the authorization on the request, for example returning only the tools the caller's scopes permit ([tools](https://modelcontextprotocol.io/specification/latest/server/tools)).

Tool annotations. The schema defines `ToolAnnotations` with `title`, `readOnlyHint` (default false), `destructiveHint` (default true, meaningful only when `readOnlyHint` is false), `idempotentHint` (default false), and `openWorldHint` (default true) ([schema.ts, 2026-07-28](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts)). The tools page warns that clients MUST treat annotations as untrusted unless they come from trusted servers ([tools](https://modelcontextprotocol.io/specification/latest/server/tools)).

Structured output. `structuredContent` is any JSON value that conforms to the tool's `outputSchema` when one is defined. If an `outputSchema` is provided, servers MUST return conforming results and clients SHOULD validate them. For compatibility a tool that returns structured content SHOULD also serialise it into a text block ([tools, structured content](https://modelcontextprotocol.io/specification/latest/server/tools)).

Errors. Protocol errors (unknown tool, malformed request) are JSON-RPC errors. Tool execution errors (validation, business rules, upstream failures) go in the result with `isError: true` so the model can self-correct ([tools, error handling](https://modelcontextprotocol.io/specification/latest/server/tools)).

Resources and prompts. Resources are application-driven context items addressed by URI, with templates (RFC 6570), `listChanged`, and per-resource subscriptions through `subscriptions/listen` ([resources](https://modelcontextprotocol.io/specification/latest/server/resources)). Prompts are user-controlled templates, typically surfaced as slash commands ([prompts](https://modelcontextprotocol.io/specification/latest/server/prompts)).

Elicitation. Servers can ask the user for input during a tool call. Form mode collects flat primitive fields against a restricted JSON Schema. URL mode sends the user to an out-of-band page for anything sensitive. Servers MUST NOT use form mode for passwords, API keys, or tokens. Under `2026-07-28` an elicitation is carried in an `InputRequiredResult` and the client retries the original call with the answer ([elicitation](https://modelcontextprotocol.io/specification/latest/client/elicitation)).

Tasks. Tasks are now an official extension, `io.modelcontextprotocol/tasks`. A server returns `resultType: "task"` with a `taskId`, TTL, and poll interval; the client polls `tasks/get`, answers mid-flight input with `tasks/update`, and may `tasks/cancel`. States are `working`, `input_required`, `completed`, `failed`, `cancelled`. Both sides must opt in ([tasks extension](https://modelcontextprotocol.io/specification/latest/basic/utilities/tasks)). The community client matrix does not list Tasks support for any major client ([client matrix](https://modelcontextprotocol.io/extensions/client-matrix)).

Pagination. Cursors are opaque strings. Page size is server-chosen. `tools/list`, `prompts/list`, `resources/list`, and `resources/templates/list` support it. Invalid cursors SHOULD return `-32602` ([pagination](https://modelcontextprotocol.io/specification/2026-07-28/server/utilities/pagination)).

## 2. MCP authorization

The authorization spec applies to HTTP transports. Stdio implementations SHOULD NOT follow it and should read credentials from the environment instead ([authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)).

Requirements for a remote server, quoted from the overview:

- Authorization servers MUST implement OAuth 2.1 ([authorization, overview 1](https://modelcontextprotocol.io/specification/latest/basic/authorization)).
- MCP servers MUST implement OAuth 2.0 Protected Resource Metadata (RFC 9728). Clients MUST use it for authorization server discovery ([authorization, overview 4](https://modelcontextprotocol.io/specification/latest/basic/authorization)).
- Authorization servers MUST provide RFC 8414 metadata or OpenID Connect Discovery; clients MUST support both ([authorization, overview 5](https://modelcontextprotocol.io/specification/latest/basic/authorization)).
- Authorization servers and clients SHOULD support Client ID Metadata Documents. They MAY support Dynamic Client Registration (RFC 7591), which is deprecated and kept for backwards compatibility ([authorization, overview 2 and 3](https://modelcontextprotocol.io/specification/latest/basic/authorization); [client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)).
- Clients MUST implement Resource Indicators (RFC 8707) and send `resource` on both the authorization and token requests. Servers MUST validate the token audience and MUST NOT accept or transit tokens issued for other resources ([authorization, resource parameter and token handling](https://modelcontextprotocol.io/specification/latest/basic/authorization)).
- PKCE is part of the OAuth 2.1 baseline; the flow diagram shows the client generating PKCE parameters before redirecting ([authorization, flow steps](https://modelcontextprotocol.io/specification/latest/basic/authorization)).
- Servers SHOULD put a `scope` parameter in the `WWW-Authenticate` challenge, and SHOULD answer insufficient scope with `403` plus `error="insufficient_scope"` so the client can step up ([authorization, scope selection and scope challenge](https://modelcontextprotocol.io/specification/latest/basic/authorization)).
- Authorization servers SHOULD return `iss` (RFC 9207) and clients MUST validate it ([authorization, response validation](https://modelcontextprotocol.io/specification/latest/basic/authorization)).

Client registration priority, quoted from the spec: use pre-registered credentials if available, else CIMD if the AS advertises `client_id_metadata_document_supported`, else DCR if `registration_endpoint` exists, else prompt the user ([client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)).

Headless agents. The OAuth Client Credentials extension (`io.modelcontextprotocol/oauth-client-credentials`) covers machine-to-machine access with `client_secret` or RFC 7523 JWT assertions. The page names CI pipelines and background services as the target ([client credentials extension](https://modelcontextprotocol.io/extensions/auth/oauth-client-credentials)). The client matrix shows no major client supporting it yet ([client matrix](https://modelcontextprotocol.io/extensions/client-matrix)).

## 3. MCP TypeScript SDK

Two release lines exist as of 2026-09-23:

- v1: `@modelcontextprotocol/sdk` 1.30.0, published 2026-07-27. Peer dependency `zod ^3.25 || ^4.0`. Node 18+ ([npm registry](https://registry.npmjs.org/@modelcontextprotocol/sdk)). The README says v1.x "continues to receive bug fixes and security updates for at least 6 months after v2's release" ([README](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/README.md)).
- v2: split packages `@modelcontextprotocol/server`, `@modelcontextprotocol/client`, `@modelcontextprotocol/core`, plus middleware `@modelcontextprotocol/node`, `/express`, `/fastify`, `/hono`, all at 2.0.0, published 2026-07-27, "released alongside the 2026-07-28 spec" ([README](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/README.md); [releases](https://github.com/modelcontextprotocol/typescript-sdk/releases)). `@modelcontextprotocol/fastify` peer-depends on `fastify ^5.2.0` ([npm registry](https://registry.npmjs.org/@modelcontextprotocol/fastify)).

High-level API (v2). `new McpServer({ name, version })`, then `server.registerTool(name, { description, inputSchema, outputSchema?, title?, annotations? }, handler)`, `registerResource`, `registerPrompt`. Schemas are Standard Schema, so Zod v4, Valibot, or ArkType all work; the examples use `import * as z from 'zod/v4'` ([README](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/README.md); [tools guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/servers/tools.md)). The SDK validates `structuredContent` against `outputSchema` before the result leaves the server and advertises the derived JSON Schema in `tools/list` ([tools guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/servers/tools.md)). A schema rejection returns an ordinary result with `isError: true` ([tools guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/servers/tools.md)).

Serving over HTTP (v2). `createMcpHandler(factory)` takes a factory that builds a fresh `McpServer` per request and returns `{ fetch, close, notify, bus }`, where `fetch` is a web-standard `(Request) => Promise<Response>`. The factory receives `era`, `authInfo`, and `requestInfo`, so you can build the instance for one caller. The handler holds nothing between requests, so it is stateless and scales horizontally. `authInfo` is pass-through: verify the bearer token in front of the handler and pass the result as `handler.fetch(request, { authInfo })` ([serve over HTTP](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/http.md)).

Fastify mount (v2), quoted from the guide:

```ts
import { createMcpFastifyApp } from "@modelcontextprotocol/fastify";
import { toNodeHandler } from "@modelcontextprotocol/node";
import { createMcpHandler, McpServer } from "@modelcontextprotocol/server";

const handler = createMcpHandler(() => {
  const server = new McpServer({ name: "notes", version: "1.0.0" });
  // registerTool(...) inside the factory
  return server;
});
const app = createMcpFastifyApp();
const node = toNodeHandler(handler);
app.all("/mcp", (request, reply) => node(request.raw, reply.raw, request.body));
```

`createMcpFastifyApp` is `Fastify()` with Host and Origin validation for DNS rebinding protection, defaulting to a `127.0.0.1` bind; binding to all interfaces drops that default and you name allowed hosts instead ([serve with Fastify](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/fastify.md)). The guide says `app` is an ordinary Fastify instance, so the route can also be registered on an existing app. The Fastify package README calls itself a "thin Fastify integration layer" exporting `createMcpFastifyApp`, `hostHeaderValidation`, and `localhostHostValidation` ([fastify package README](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/packages/middleware/fastify/README.md)). No other Fastify integration was checked; this is the official one.

Legacy clients. By default `createMcpHandler` serves 2025-era clients statelessly from the same factory (`legacy: 'stateless'`). `legacy: 'reject'` makes the endpoint modern-only and answers `initialize` with `400` and `-32022`. Under the stateless posture a legacy `GET` (standalone SSE) and `DELETE` answer `405`, so there are no sessions in either posture unless you hand-wire `NodeStreamableHTTPServerTransport` with `sessionIdGenerator` ([legacy clients](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/legacy-clients.md); [sessions, state, scaling](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/sessions-state-scaling.md)).

Authorization helpers (v2). `requireBearerAuth({ verifier, requiredScopes, resourceMetadataUrl })` exists in `@modelcontextprotocol/server` (web-standard) and `@modelcontextprotocol/express`. You supply one function, `verifyAccessToken(token) => AuthInfo` with `clientId`, `scopes`, `expiresAt`. Missing or bad tokens get `401 invalid_token`; missing scopes get `403 insufficient_scope`; both carry `WWW-Authenticate`. `mcpAuthMetadataRouter` / `oauthMetadataResponse` serve the RFC 9728 document at `/.well-known/oauth-protected-resource/mcp`. The v1 authorization-server helpers are frozen in `@modelcontextprotocol/server-legacy/auth`; the guide says to "use a dedicated identity provider for new servers" ([require authorization](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/authorization.md)). There is no Fastify-specific `requireBearerAuth`; the web-standard gate returns either an `AuthInfo` or a challenge `Response`, which a Fastify `preHandler` can adapt (inference, not from the docs).

Zod. v2 packages depend on `zod ^4.2.0`; a workspace pinned to zod 3 gets nested zod 4 copies ([upgrade guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/migration/upgrade-to-v2.md)). OpenLaw is already on zod 4.6.x and Fastify 5.12 (repo `package.json` files), so this is not a blocker.

Caveats:

- v2 shipped on 2026-07-27 and the README says pull requests are limited "while v2 settles" ([README](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/README.md)). Expect churn.
- The SDK protocol-versions page says every revision from `2024-10-07` through `2025-11-25` is the legacy era and that the v2 client defaults to the legacy handshake (`mode` absent or `'legacy'`), with `'auto'` probing `server/discover` first ([protocol versions](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/protocol-versions.md)). That default tells you the mainstream clients were still legacy at release. Serve both eras.
- Under legacy stateless mode there is no standalone GET stream, so `notifications/tools/list_changed` cannot reach a legacy client. Modern clients use `subscriptions/listen` ([legacy clients](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/legacy-clients.md); [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)).
- The structured-result wire encoding differs by era ([tools guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/servers/tools.md)). The SDK handles it.

## 4. better-auth's relevant plugins

Versions read from npm on 2026-09-23: `better-auth` 1.7.5, `@better-auth/mcp` 1.7.5, `@better-auth/oauth-provider` 1.7.5, `@better-auth/api-key` 1.7.5, `@better-auth/cimd` 1.7.5, all published 2026-09-14 ([npm registry](https://registry.npmjs.org/better-auth)). OpenLaw pins `better-auth ~1.7.5`.

The `mcp` plugin. It "transforms your Better Auth server into an OAuth 2.1 provider for Model Context Protocol clients". It extends the `oauth-provider` plugin and adds MCP defaults plus the RFC 9728 protected resource document. The JWT plugin is required: "it provides the stable signing key used for ID tokens and access tokens, and exposes the `/jwks` endpoint that resource servers use to verify them". Config is flat: `loginPage`, `consentPage`, `resource` (an HTTPS URL with no query, fragment, or credentials; HTTP only on loopback), and optional `allowDynamicClientRegistration`. The docs state "MCP deprecates Dynamic Client Registration (DCR), so Better Auth never enables DCR implicitly" and recommend installing `@better-auth/cimd` with `metadataProfile: "mcp-2026-07-28"`. Endpoints: `/oauth2/authorize`, `/oauth2/token`, `/oauth2/userinfo`, `/oauth2/register` when DCR is on, `/.well-known/oauth-authorization-server`, `/.well-known/oauth-protected-resource`. The plugin targets "the MCP 2026-07-28 profile" and "the official MCP TypeScript SDK v2" ([mcp plugin](https://www.better-auth.com/docs/plugins/mcp)).

Token verification with the `mcp` plugin. `requireMcpAuth(auth, (request) => handler.fetch(request), { resource, requiredScopes })` wraps a web-standard handler. It "reads the `Authorization` header, verifies access tokens against the authorization server's JSON Web Key Set (JWKS), and checks the signature, issuer, audience, and expiry". A token missing a required scope gets `403` with an `insufficient_scope` challenge. For a resource server on a different host, `createMcpProtectedRequestHandler({ issuer, audience, jwksUrl }, async (request, accessTokenClaims) => ...)` does the same with explicit config ([mcp plugin](https://www.better-auth.com/docs/plugins/mcp)). Quoted setup:

```ts
plugins: [
  jwt(),
  mcp({ loginPage: "/sign-in", consentPage: "/consent", resource: "https://api.example.com/mcp" }),
  cimd({ fetchClientMetadataResource, metadataProfile: "mcp-2026-07-28" }),
];
```

The `oauth-provider` plugin. This is the general OAuth 2.1 authorization server: `authorization_code` with S256 PKCE (PKCE required for public clients), `refresh_token`, `client_credentials` (admin-controlled), optional `device_code`. It supports DCR (`allowDynamicClientRegistration`), CIMD through `@better-auth/cimd`, consent pages with `skip_consent` for trusted clients, JWT access tokens with `aud` set to the requested resource, opaque tokens with `/oauth2/introspect`, RFC 9207 `iss`, DPoP, and per-endpoint rate limits. Resource servers verify with `oauthProviderResourceClient(auth)` and `serverClient.verifyAccessTokenRequest(req, { verifyOptions: { issuer, audience }, requiredScopes })`, or by JWKS directly. The docs say "Use the `@better-auth/mcp` plugin when an MCP server is one of your protected resources" and "Do not register both `mcp()` and `oauthProvider()`" ([oauth-provider plugin](https://www.better-auth.com/docs/plugins/oauth-provider)). The 1.5 release post introduced `@better-auth/oauth-provider` as "a full OAuth 2.1 authorization server with OIDC compatibility" ([Better Auth 1.5](https://better-auth.com/blog/1-5)).

The `oidc-provider` plugin. The docs page at `/docs/plugins/oidc-provider` returned 404 on 2026-09-23, and no `@better-auth/oidc-provider` package exists on npm. A search snippet of the old page said it was "in active development and may not be suitable for production use" ([search result, old page](https://www.better-auth.com/docs/plugins/oidc-provider.mdx)). Whether it is formally deprecated is unverified. The current docs route everything through `oauth-provider` and `mcp`.

The `api-key` plugin. Keys are created server-side with `auth.api.createApiKey({ body: { userId, name, prefix, expiresIn, remaining, refillAmount, refillInterval, rateLimitEnabled, rateLimitTimeWindow, rateLimitMax, permissions, metadata } })` or client-side by the signed-in user. Keys are owned by a user or, with `references: "organization"`, by an organization. `auth.api.verifyApiKey({ body: { key, permissions } })` returns `{ valid, error, key }`. Keys are hashed by default; `disableKeyHashing` exists with a warning not to use it ([api-key plugin](https://www.better-auth.com/docs/plugins/api-key); [reference](https://www.better-auth.com/docs/plugins/api-key/reference)).

How a key maps to a session. The default header is `x-api-key`, configurable with `apiKeyHeaders` or `customAPIKeyGetter(ctx)`. With `enableSessionForAPIKeys: true`, "a valid API key in the headers" makes `auth.api.getSession()` return a mock session for the owning user; organization-owned keys cannot mock a user session. The docs warn: "This is generally not recommended, as it can lead to security issues if not used carefully. A leaked api key can be used to impersonate a user" ([api-key advanced](https://www.better-auth.com/docs/plugins/api-key/advanced)).

Rate limits and expiry. Plugin defaults are `rateLimit: { enabled: true, timeWindow: 1 day, maxRequests: 10 }`, a sliding window per key; per-key overrides at creation. Verifying a key and then fetching a session counts twice. `keyExpiration.defaultExpiresIn` defaults to `null` (never expires); `maxExpiresIn` defaults to 365 days. `remaining` counts down and the key is disabled and removed at 0; `refillInterval` and `refillAmount` restore it ([api-key advanced](https://www.better-auth.com/docs/plugins/api-key/advanced); [reference](https://www.better-auth.com/docs/plugins/api-key/reference)).

Permissions. `permissions` is a record of resource to actions, for example `{ projects: ["read"] }`, with `permissions.defaultPermissions` as a static object or a function of the owner ([reference](https://www.better-auth.com/docs/plugins/api-key/reference)).

The `bearer` plugin. It lets a client use its own session token as `Authorization: Bearer` instead of a cookie; the token arrives in the `set-auth-token` response header after sign-in. The docs say it is "intended only for APIs that don't support cookies" and that "improper implementation could easily lead to security vulnerabilities" ([bearer plugin](https://www.better-auth.com/docs/plugins/bearer)). It is not an MCP mechanism.

Which plugin for MCP in 2026. The better-auth docs point interactive MCP clients at `mcp()` (on top of `oauth-provider`) with `cimd()`, and treat `oauthProvider()` alone as the choice when the MCP server is not one of the protected resources ([mcp plugin](https://www.better-auth.com/docs/plugins/mcp); [oauth-provider plugin](https://www.better-auth.com/docs/plugins/oauth-provider)). Nothing in the better-auth docs pairs `api-key` with MCP; that pairing is vendor precedent (Section 2), not a better-auth recommendation.

## 5. OpenAPI-to-MCP

Anthropic's engineering guidance. "More tools don't always lead to better outcomes. A common error we've observed is tools that merely wrap existing software functionality or API endpoints—whether or not the tools are appropriate for agents." The post recommends a smaller set of consolidated tools aimed at high-impact workflows, consistent namespacing (`asana_projects_search`), natural-language identifiers over UUIDs in results, `concise` versus `detailed` response formats, pagination and truncation with steering text, and descriptions written "as if onboarding a new team member" ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)).

MCP spec on tool lists. Servers SHOULD return tools in a deterministic order because the list sits in model context and affects prompt-cache hits; `tools/list` results carry `ttlMs` and `cacheScope` so clients can cache the list ([tools](https://modelcontextprotocol.io/specification/latest/server/tools)). Claude Code caps a single tool result at 25,000 tokens by default and warns at 10,000 ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)).

Stainless. The generated server uses "a code tool architecture" with two tools, a code-execution tool and a docs-search tool: "A small number of tools take up less space in an LLM's context window, and multiple operations can be performed in a single code tool call with arbitrary complexity" ([Stainless MCP docs](https://www.stainless.com/docs/mcp/)). Their "dynamic tools" mode exposes three meta-tools, `list_api_endpoints`, `get_api_endpoint_schema`, `invoke_api_endpoint`, "without requiring the entire API schema to be loaded into its context window at once" ([Stainless changelog, MCP dynamic tools](https://www.stainless.com/changelog/mcp-dynamic-tools)).

Speakeasy. Generation from OpenAPI is convenient because "Your OpenAPI document becomes the single source of truth", but "AI agents need more context than human developers to use APIs effectively", not all endpoints are task-shaped, and thin specs cause hallucination. Their `x-speakeasy-mcp` extension overrides tool name and description, and tags tools with scopes such as `read` and `write` so a server can start with only a subset (`--scope`), including "Read and write, but not destructive operations" ([Speakeasy, generating MCP tools from OpenAPI](https://www.speakeasy.com/mcp/tool-design/generate-mcp-tools-from-openapi)).

Kong. The AI MCP Proxy plugin maps one OpenAPI operation to one tool, taking the name from `operationId` and the description from `summary`. It layers tool ACLs (default allow/deny plus per-tool rules by consumer or consumer group) and tag-based aggregation ([Kong AI MCP Proxy](https://developer.konghq.com/plugins/ai-mcp-proxy/)).

Cloudflare. Their own servers are split into "domain-specific servers" with "purpose-built tools for a specific product area" plus a separate Code Mode server for broad API access ([cloudflare/mcp-server-cloudflare](https://github.com/cloudflare/mcp-server-cloudflare)). Their tool guide says "The `description` parameter is critical — it is what the LLM reads to decide whether and when to call your tool" ([Cloudflare Agents, tools](https://developers.cloudflare.com/agents/model-context-protocol/tools/)).

Vendor practice. Stripe exposes about ten tools, four of which are meta-tools (`stripe_api_search`, `stripe_api_details`, `stripe_api_read`, `stripe_api_write`) over a curated list of API methods, "without increasing the context window unnecessarily" ([Stripe MCP](https://docs.stripe.com/mcp)). Atlassian defaults to "discovery and execute methods" and only returns a flat tool list when asked with `?tools=all` ([Atlassian MCP getting started](https://support.atlassian.com/atlassian-rovo-mcp-server/docs/getting-started-with-the-atlassian-remote-mcp-server/)).

Summary of the recorded arguments. For curated, task-shaped tools: fewer tools mean less context and better tool choice (Anthropic, Stainless, GitHub's toolset rationale in Section 6), endpoints are not task-shaped (Speakeasy), and descriptions carry the weight (Cloudflare, Anthropic). For 1:1 generation: one source of truth and low maintenance (Speakeasy, Kong), but every generator then adds a filter: scopes, ACLs, toolsets, or meta-tools, to keep the exposed count small.

## 8. Audit and safety patterns

The MCP security best practices document ([security best practices, 2026-07-28](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices), canonical path `/docs/2026-07-28/tutorials/security/security_best_practices`) covers:

- Confused deputy. An MCP proxy that uses a static client id with a third-party AS, lets clients register dynamically, and relies on a consent cookie can be tricked into issuing codes to an attacker. Proxies MUST keep a per-user registry of approved `client_id` values, show an MCP-owned consent page naming the client and its `redirect_uri`, validate `redirect_uri` by exact match, and bind `state` to consent.
- Token passthrough. "MCP servers MUST NOT accept any tokens that were not explicitly issued for the MCP server." The listed risks include "Accountability and audit trail issues: the MCP Server will be unable to identify or distinguish between MCP Clients".
- State handle hijacking (the replacement for session hijacking now that sessions are gone). Servers "MUST NOT treat possession of a state handle as authentication", SHOULD mint random handles, and SHOULD key stored state as `<user_id>:<handle>` with the user id from the verified token.
- SSRF during OAuth discovery, OAuth URL scheme validation, local server compromise, mix-up attacks, localhost redirect impersonation, and CIMD trust policies.
- Scope minimization. Start with a minimal scope set, challenge for more with `WWW-Authenticate scope=...`, and "Log elevation events (scope requested, granted subset) with correlation IDs". Listed mistakes include "wildcard or omnibus scopes" and "Treating claimed scopes in token as sufficient without server-side authorization logic".

Human in the loop. The tools spec says there "SHOULD always be a human in the loop with the ability to deny tool invocations", that applications SHOULD "present confirmation prompts to the user for operations", and that clients SHOULD "prompt for user confirmation on sensitive operations", "show tool inputs to the user before calling the server", and "log tool usage for audit purposes". Servers MUST "validate all tool inputs", "implement proper access controls", "rate limit tool invocations", and "sanitize tool outputs" ([tools](https://modelcontextprotocol.io/specification/latest/server/tools)). Clients decide their own gating: ChatGPT requires manual confirmation before write actions and skips approval for read-only tools ([OpenAI MCP docs](https://developers.openai.com/api/docs/mcp)); Cursor "requests user approval before tool execution" by default ([Cursor MCP docs](https://cursor.com/docs/context/mcp)); Claude Code prompts before using project-scoped servers ([Claude Code MCP docs](https://code.claude.com/docs/en/mcp)). Stripe adds a server-side gate: some writes return an approval URL, the human approves in Stripe, and the agent retries with a 24-hour approval token ([Stripe MCP](https://docs.stripe.com/mcp)). The Tasks extension names "human-in-the-loop workflows" and "approval gates" as a use case for `input_required` ([tasks](https://modelcontextprotocol.io/specification/latest/basic/utilities/tasks)).

Actor attribution. No first-party source prescribes a separate "agent actor" field in an audit log. The pieces that exist: clients SHOULD send `io.modelcontextprotocol/clientInfo` on every request ([changelog](https://modelcontextprotocol.io/specification/latest/changelog)); servers MUST derive user identity from the verified token, for example the `sub` claim, and MUST NOT trust client-supplied identity ([elicitation, identifying the user](https://modelcontextprotocol.io/specification/latest/client/elicitation)); a distinct OAuth client id per MCP client is what makes the audit trail readable ([security best practices, token passthrough](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices)). Stripe exposes "MCP tool call logs in Workbench" ([Stripe MCP](https://docs.stripe.com/mcp)); Atlassian tells admins to "monitor audit logs for unusual activity" ([Atlassian MCP getting started](https://support.atlassian.com/atlassian-rovo-mcp-server/docs/getting-started-with-the-atlassian-remote-mcp-server/)); Claude for Government logs every tool invocation along the path "User → Claude → MCP service → connected service" ([MCP connectors](https://support.claude.com/en/articles/14503689-mcp-connectors)).

Per-token scopes and rate limits. The authorization spec wants scope challenges per operation and `403 insufficient_scope` for step-up ([authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)). better-auth's `api-key` plugin gives each key its own `permissions`, `rateLimitMax` per `rateLimitTimeWindow`, `expiresIn`, and `remaining` budget ([api-key advanced](https://www.better-auth.com/docs/plugins/api-key/advanced)). Linear and GitHub ship read-only entry points as separate URLs or scopes (Section 6).

Prompt injection. Supabase calls it "the primary attack vector unique to LLMs" and mitigates with `read_only` and `project_ref` scoping ([Supabase MCP](https://supabase.com/docs/guides/getting-started/mcp)). Stripe says to "enable human confirmation of tools and exercise caution when using the Stripe MCP with other servers to avoid prompt injection attacks" ([Stripe MCP](https://docs.stripe.com/mcp)).

## What this suggests for OpenLaw

- Mount one Streamable HTTP endpoint under the API (for example `/mcp`) with SDK v2's `createMcpHandler` and `@modelcontextprotocol/fastify`, keep the default dual-era posture so 2025-era clients still connect, and do not add the old HTTP+SSE transport ([serve with Fastify](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/fastify.md); [legacy clients](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/legacy-clients.md); [changelog, deprecated 2](https://modelcontextprotocol.io/specification/latest/changelog)).
- Make the endpoint stateless. Build the `McpServer` per request from `authInfo`, so the tool list already reflects the caller's role and scopes; the spec allows the list to vary by authorization but not by connection ([serve over HTTP](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/serving/http.md); [tools](https://modelcontextprotocol.io/specification/latest/server/tools)).
- Use better-auth's `mcp()` plugin with `jwt()` and `cimd()` for interactive clients (Claude.ai, Claude Code, Cursor, VS Code, ChatGPT), and leave DCR off unless a target client cannot do CIMD; OpenLaw is already an OAuth provider candidate because it runs better-auth ([mcp plugin](https://www.better-auth.com/docs/plugins/mcp); [client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration)).
- Verify tokens in a Fastify `preHandler` with `requireMcpAuth` or `createMcpProtectedRequestHandler`, which check signature, issuer, audience, and expiry; audience binding is a MUST and token passthrough is forbidden ([mcp plugin](https://www.better-auth.com/docs/plugins/mcp); [authorization, token handling](https://modelcontextprotocol.io/specification/latest/basic/authorization)).
- Add API keys from `@better-auth/api-key` for headless agents (Messages API `authorization_token`, CI, `.mcp.json` with `${OPENLAW_API_KEY}`), accepted on the same URL as OAuth, the way Stripe, Linear, and GitHub do it; give each key `permissions`, an expiry, and a rate limit, and bind it to a user so the four OpenLaw roles still apply ([api-key advanced](https://www.better-auth.com/docs/plugins/api-key/advanced); [Stripe MCP](https://docs.stripe.com/mcp); [Claude Code MCP docs](https://code.claude.com/docs/en/mcp)).
- Curate a small set of task-shaped tools instead of generating one tool per OpenAPI route; group them into toolsets that a deployer can enable per key or per client, with a default set, as GitHub's `--toolsets` and Supabase's `features` do ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents); [github-mcp-server README](https://github.com/github/github-mcp-server); [Supabase MCP](https://supabase.com/docs/guides/getting-started/mcp)).
- Offer a read-only mode as a first-class switch (scope, header, or `/readonly` URL) and make it win over any explicit tool request, matching GitHub and Linear ([remote-server.md](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md); [Linear MCP](https://linear.app/docs/mcp)).
- Set `annotations` on every tool (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint: false`), because ChatGPT skips approval only for read-only tools and clients use the hints for confirmation prompts, and return `structuredContent` with an `outputSchema` derived from the existing Zod route schemas ([schema.ts](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/schema/2026-07-28/schema.ts); [OpenAI MCP docs](https://developers.openai.com/api/docs/mcp); [tools guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/docs/servers/tools.md)).
- Gate destructive tools server-side, not only in the client: either exclude them from the default toolset or require a human approval step like Stripe's approval token, and consider the Tasks extension's `input_required` state for that once clients support it ([Stripe MCP](https://docs.stripe.com/mcp); [tasks](https://modelcontextprotocol.io/specification/latest/basic/utilities/tasks)).
- Record an agent actor in the audit log: the verified user from the token `sub`, the OAuth client id or API key id, and the `clientInfo` name and version sent on each request, so agent actions are distinguishable from the same user's UI actions ([elicitation, identifying the user](https://modelcontextprotocol.io/specification/latest/client/elicitation); [changelog, major change 2](https://modelcontextprotocol.io/specification/latest/changelog); [security best practices, token passthrough](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices)).
- Report business errors as tool results with `isError: true` carrying the RFC 9457 problem detail text, and keep JSON-RPC errors for protocol faults, so the model can self-correct ([tools, error handling](https://modelcontextprotocol.io/specification/latest/server/tools)).
- Keep scopes few and specific (for example `contracts:read`, `matters:write`), challenge with `WWW-Authenticate scope=` on `403`, and log scope elevation with correlation ids; avoid one omnibus scope ([security best practices, scope minimization](https://modelcontextprotocol.io/specification/latest/basic/security_best_practices); [authorization, scope challenge](https://modelcontextprotocol.io/specification/latest/basic/authorization)).

### What the MCP specification says

The tools page allows the list to vary by authorization and forbids varying it by connection: "Servers that declare the `tools` capability MUST respond to `tools/list` requests with the set of tools currently available to the requesting client. This set MAY be empty and MAY change over time (see List Changed Notification), but MUST NOT vary per-connection or as a side effect of other requests on the connection. The set MAY vary by the authorization presented on the request — for example, returning only the tools the caller's granted scopes permit — since credentials are per-request input, not connection state" ([tools](https://modelcontextprotocol.io/specification/latest/server/tools)). The same page requires servers to "Implement proper access controls".

The authorization page covers the call-time side. A token with too little scope gets "HTTP 403 Forbidden" with `error="insufficient_scope"` and a `scope=` list, and "Servers MUST account for scope hierarchies, where a broader scope implies narrower ones, when deciding whether a token is sufficient for an operation" ([authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)). The spec says nothing about audiences or roles as such; role is a server concern expressed through scopes and access checks.

### Patterns observed

- One server, one URL, for every audience. No vendor documents a second MCP server for its limited audience. Identity comes from the token and the product's existing permission model decides what a call returns: Atlassian ([authentication and authorization](https://developer.atlassian.com/cloud/rovo-mcp/guides/authentication-and-authorization/)), HubSpot ([remote server guide](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/integrate-with-the-remote-hubspot-mcp-server)), LawVu ([LawVu MCP server](https://help.lawvu.com/en/articles/15266786-lawvu-mcp-server)), Ironclad ([connect a client](https://support.ironcladapp.com/hc/en-us/articles/39887632957463-Connect-an-MCP-Client-to-Ironclad-MCP-Server)), Freshworks ([MCP security](https://support.freshservice.com/support/solutions/articles/50000014410-freshworks-mcp-security)), ServiceNow ([FAQ](https://www.servicenow.com/community/servicenow-otto-articles/mcp-server-console-faq/ta-p/3550125)), GitHub ([policies and governance](https://github.com/github/github-mcp-server/blob/main/docs/policies-and-governance.md)).
- When a vendor names the limited audience, it excludes them. Freshworks: "Only users with administrator or agent roles can access MCP capabilities" ([MCP security](https://support.freshservice.com/support/solutions/articles/50000014410-freshworks-mcp-security)). Supabase: "you should not give it to your customers or end users" ([Supabase MCP](https://supabase.com/docs/guides/getting-started/mcp)). Atlassian ships no request or portal tools and gates portal Rovo agents to Atlassian Accounts ([supported tools](https://developer.atlassian.com/cloud/rovo-mcp/guides/supported-tools/); [virtual service agent](https://support.atlassian.com/jira-service-management-cloud/docs/set-up-your-virtual-agent-in-jira-service-management/)). No vendor in this list documents MCP for a customer, requester, or portal user.
- The tool list varies by grant, not by audience. HubSpot: "Tool availability varies by HubSpot subscription, user permissions, and account configuration" ([remote server guide](https://developers.hubspot.com/docs/apps/developer-platform/build-apps/integrate-with-the-remote-hubspot-mcp-server)). Notion hides session tools when the connection lacks the capability ([supported tools](https://developers.notion.com/guides/mcp/mcp-supported-tools)). GitHub filters by classic PAT scope ([scope filtering](https://github.com/github/github-mcp-server/blob/main/docs/scope-filtering.md)). Atlassian shapes the list by auth method and admin-enabled permission groups ([supported tools](https://developer.atlassian.com/cloud/rovo-mcp/guides/supported-tools/)). Ironclad goes the other way: the list is enabled per company and a tool can appear but not work in a session ([connect a client](https://support.ironcladapp.com/hc/en-us/articles/39887632957463-Connect-an-MCP-Client-to-Ironclad-MCP-Server)).
- Visible-but-forbidden is handled at call time, three ways. GitHub with OAuth returns a scope challenge; GitHub with a fine-grained PAT or App token lets the API reject ([scope filtering](https://github.com/github/github-mcp-server/blob/main/docs/scope-filtering.md)). ServiceNow denies through ACLs, including tool-level execute ACLs ([FAQ](https://www.servicenow.com/community/servicenow-otto-articles/mcp-server-console-faq/ta-p/3550125)). Notion returns `object_not_found` and tells the model to read it "as a permissions signal" ([supported tools](https://developers.notion.com/guides/mcp/mcp-supported-tools)). The spec blesses the first: `403` with `insufficient_scope` ([authorization](https://modelcontextprotocol.io/specification/latest/basic/authorization)).
- Read-only is the one split vendors build into the URL or scope. Linear `/readonly` and the `read` scope ([Linear MCP](https://linear.app/docs/mcp)), GitHub `/readonly` ([remote server](https://github.com/github/github-mcp-server/blob/main/docs/remote-server.md)), Supabase `read_only=true` ([Supabase MCP](https://supabase.com/docs/guides/getting-started/mcp)), Ironclad's read-only `conversational_search` ([Ironclad MCP Server](https://support.ironcladapp.com/hc/en-us/articles/39887091143319-Ironclad-MCP-Server)). Nobody builds an audience split the same way.
- Admin gating sits in front of user gating. Atlassian disables `delete_jira` and `manage_jira` groups by default ([authentication and authorization](https://developer.atlassian.com/cloud/rovo-mcp/guides/authentication-and-authorization/)). ServiceNow needs `sn_mcp_server.viewer` to call stock tools and admin-built servers to expose anything else ([FAQ](https://www.servicenow.com/community/servicenow-otto-articles/mcp-server-console-faq/ta-p/3550125)). HubSpot's admin connects first ([HubSpot MCP](https://developers.hubspot.com/mcp)). Notion Enterprise owners approve clients ([Connect AI tools with Notion MCP](https://www.notion.com/help/notion-mcp)). LawVu's Organisation Admin enables the feature ([LawVu MCP server](https://help.lawvu.com/en/articles/15266786-lawvu-mcp-server)).
- Separate servers exist only when an admin builds them. ServiceNow's MCP Server Console lets AI administrators "create MCP servers and configure which tools they expose" ([exploring MCP Server Console](https://www.servicenow.com/docs/r/intelligent-experiences/exploring-mcp-server-console.html)). That is the only first-party route to a per-audience server, and it is a deployer choice, not a vendor default.
- Nobody names tools by audience. Grouping is by resource (Freshservice), product area (GitHub toolsets, Atlassian permission groups), capability (Notion), skill (Sentry), or API group (DocuSign). The closest thing to audience-shaped naming is Intercom's `add_internal_note`, whose description states the customer never sees it ([Intercom MCP guide](https://developers.intercom.com/docs/guides/mcp)).

## 10. What Claude, ChatGPT and Microsoft 365 Copilot expect from a remote server

This section answers one question: what does each of the three big MCP clients need from OpenLaw's single Streamable HTTP endpoint, with better-auth as the authorization server and API keys as a second credential. Section 7 gave the short version. This section goes deeper, one client at a time, on seven topics: registration, authorization, network, protocol, tools, confirmation, and identity. Every claim links to a vendor page read on 2026-09-23. Where a vendor page is silent the text says "not documented". Where the only evidence is a user report on a vendor's issue tracker, the text says so.

Vocabulary for the protocol topic comes from the spec's own versioning page: "Modern" means revision `2026-07-28` and later (per-request `_meta`, `server/discover`, no `initialize`), "Legacy" means `2025-11-25` and earlier (the `initialize` handshake), and "Dual-era" means an implementation that speaks both ([versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)).

### Claude

Claude Code is a separate client that connects from the user's machine. The Messages API MCP connector is a fourth surface with no user in the loop.

Custom connectors are per user on Free (one connector), Pro and Max, and admin-only on Team and Enterprise: "only Owners can add them to Team and Enterprise plans" ([get started with custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)). "Before members of Team and Enterprise plans can use connectors, an Owner or Primary Owner needs to enable them", and members then connect individually ([use connectors](https://support.claude.com/en/articles/11176164-use-connectors-to-extend-claude-s-capabilities)). The add dialog takes a name, the MCP server URL, an authentication mode ("Sign in now", "Sign in when needed", "No sign-in"), an OAuth client choice ("Use Claude's published identity" for CIMD, "Register automatically" for DCR, "Use your own OAuth client" for a client id plus optional secret), up to four request headers in beta with the standard names `authorization`, `x-api-key` and `x-auth-token`, and a transport override. There is no scopes field. "Authentication settings (OAuth credentials and request headers) can't be changed after a connector is added" ([remote MCP](https://claude.com/docs/connectors/custom/remote-mcp)). Admins can prefill the dialog with `https://claude.ai/admin-settings/connectors?modal=add-custom-connector&connectorName=NAME&connectorUrl=ENCODED_URL` ([directory vs custom](https://claude.com/docs/connectors/building/directory-vs-custom)). Claude Code adds a server with `claude mcp add --transport http <name> <url>` at local, project or user scope, prompts before using project-scoped `.mcp.json` servers, and lets an enterprise pin the set with `managed-mcp.json`, `allowedMcpServers` and `deniedMcpServers` keyed by `serverUrl` ([Claude Code MCP](https://code.claude.com/docs/en/mcp); [managed MCP](https://code.claude.com/docs/en/managed-mcp)). claude.ai connectors also appear inside Claude Code when the user is logged in with a subscription ([Claude Code MCP](https://code.claude.com/docs/en/mcp)). The Messages API has no registration; each request carries `mcp_servers[]` with `url`, `name` and optional `authorization_token` ([MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)).

Authorization. The hosted surfaces support `oauth_dcr`, `oauth_cimd`, `oauth_anthropic_creds` (directory only), `custom_connection`, `static_headers` (beta) and `none` ([authentication](https://claude.com/docs/connectors/building/authentication)). The one redirect URI to register is `https://claude.ai/api/mcp/auth_callback` (same page). The CIMD rule is strict: "Claude selects CIMD only when your authorization server metadata advertises both `"client_id_metadata_document_supported": true` and `"none"` in `token_endpoint_auth_methods_supported` ... If either is missing, Claude falls back to DCR" (same page). The hosted CIMD document is `https://claude.ai/oauth/mcp-oauth-client-metadata`, `client_name` "Claude", `redirect_uris` `["https://claude.ai/api/mcp/auth_callback"]`, `token_endpoint_auth_method` "none" ([CIMD document](https://claude.ai/oauth/mcp-oauth-client-metadata)). Anthropic warns that "DCR causes Claude to register a new client on every fresh connection" ([authentication](https://claude.com/docs/connectors/building/authentication)). PKCE is always on: "Claude includes a PKCE `code_challenge` with `code_challenge_method=S256` on every authorization request, regardless of which registration mechanism it uses" (same page). "Claude sends the RFC 8707 `resource` parameter on authorization and token requests, set to the canonical form of your MCP server URL" ([troubleshooting](https://claude.com/docs/connectors/building/troubleshooting)). Claude reads `WWW-Authenticate: Bearer resource_metadata="..."` only on a `401`, then probes `/.well-known/oauth-protected-resource/<path>`, then `/.well-known/oauth-protected-resource`, then `/.well-known/oauth-authorization-server`, then `/.well-known/openid-configuration`, and uses only the first `authorization_servers` entry ([authentication](https://claude.com/docs/connectors/building/authentication); [troubleshooting](https://claude.com/docs/connectors/building/troubleshooting)). Scopes come from the `401` challenge first, else `scopes_supported`, plus `offline_access` when the AS lists it; a `403 insufficient_scope` triggers step-up ([lazy authentication](https://claude.com/docs/connectors/building/lazy-authentication)). Client credentials is out: "A pure machine-to-machine `client_credentials` grant ... is not supported. Every connection requires user consent" ([authentication](https://claude.com/docs/connectors/building/authentication)). Static headers are the API key path on claude.ai, in beta: "Claude sends the value exactly as you enter it. It does not add an authentication scheme" ([remote MCP](https://claude.com/docs/connectors/custom/remote-mcp)). Discovery, registration and token endpoints get 10 seconds; refresh gets 30 ([authentication](https://claude.com/docs/connectors/building/authentication)).

Claude Code runs DCR by default, discovers CIMD automatically since 2.1.81, and takes a pre-registered client with `--client-id` and `--client-secret` ([Claude Code MCP](https://code.claude.com/docs/en/mcp)). Its CIMD document is `https://claude.ai/oauth/claude-code-client-metadata` with `redirect_uris` `["http://localhost/callback","http://127.0.0.1/callback"]`; "your authorization server must accept both with the port component ignored" ([authentication](https://claude.com/docs/connectors/building/authentication); [Claude Code CIMD](https://claude.ai/oauth/claude-code-client-metadata)). The runtime redirect is `http://localhost:PORT/callback` on a random port ([Claude Code MCP](https://code.claude.com/docs/en/mcp)). It checks RFC 9728 first, then RFC 8414, and the v2 runtime "Fails an MCP OAuth sign-in whose authorization response names an unexpected issuer" (same page). PKCE and the `resource` parameter are not documented for Claude Code. Static tokens go in `--header "Authorization: Bearer ..."`, in `.mcp.json` `headers` with `${VAR}` expansion, or from a `headersHelper` script (same page). The Messages API runs no flow; "API consumers are expected to handle the OAuth flow and obtain the access token prior to making the API call" ([MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)).

Network. "Custom connectors connect to your MCP server from Anthropic's cloud, not from your local device" ([use connectors](https://support.claude.com/en/articles/11176164-use-connectors-to-extend-claude-s-capabilities)). Claude rejects hosts that resolve to private, CGNAT, loopback or link-local addresses, "connectors are IPv4-only", and a redirect to another host drops `Authorization` ([troubleshooting](https://claude.com/docs/connectors/building/troubleshooting)). Outbound MCP calls come from `160.79.104.0/21` ([IP addresses](https://platform.claude.com/docs/en/api/ip-addresses)); the range is shared across all customers ([authentication](https://claude.com/docs/connectors/building/authentication)). Enterprise customers can ask for MCP tunnels (`cloudflared` plus Anthropic's `mcp-proxy`) for RFC 1918 upstreams ([MCP tunnels](https://claude.com/docs/connectors/mcp-tunnels/overview)). Claude Code connects from the user's machine and can reach localhost ([troubleshooting](https://claude.com/docs/connectors/building/troubleshooting)). The Messages API needs a public HTTP server ([MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)).

Protocol. Anthropic announced `2026-07-28` support with "Support is being rolled out across Claude products soon" and no per-surface list ([bringing MCP 2026-07-28 to Claude](https://claude.com/blog/bringing-mcp-2026-07-28-to-claude)). No Anthropic doc names the revision claude.ai speaks. User reports on Anthropic's tracker from 2026-09 show claude.ai sending `server/discover` and `tools/list` with `proto=2026-07-28`, and Cowork negotiating `2026-07-28` with `elicitation` in `clientCapabilities` ([issue 1027](https://github.com/anthropics/claude-ai-mcp/issues/1027); [issue 1046](https://github.com/anthropics/claude-ai-mcp/issues/1046)). The developer testing page still describes the classic `initialize` handshake ([testing](https://claude.com/docs/connectors/building/testing)). Transport is Streamable HTTP; a URL ending in `/sse` selects SSE ([remote MCP](https://claude.com/docs/connectors/custom/remote-mcp)). Claude Code's v2 runtime uses TypeScript SDK 2.0, "which adds MCP protocol revision 2026-07-28"; it "Asks HTTP servers whether they support the newer revision, and uses it with those that do", with `MCP_PROTOCOL_NEGOTIATION=auto|legacy` and `MCP_SDK_GENERATION=v1|v2`; `--transport sse` is deprecated and `http` falls back to SSE since 2.1.265 ([Claude Code MCP](https://code.claude.com/docs/en/mcp)). The Messages API accepts Streamable HTTP and SSE and does not name a revision ([MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)).

Tools. claude.ai fetches the list and caches it; an Anthropic collaborator wrote "At the moment we cache the list for 1h" ([issue 45](https://github.com/anthropics/claude-ai-mcp/issues/45), user-facing comment, not a doc). Users disable tools per conversation from the "Search and tools" menu ([get started with custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)) and can set a tool to Blocked under Customize > Connectors ([remote MCP](https://claude.com/docs/connectors/custom/remote-mcp)). Annotations drive permissions: "Every tool must include a `title` and the applicable hint ... These determine auto-permissions in Claude: read-only tools can run without per-call confirmation; destructive tools always prompt" ([review criteria](https://claude.com/docs/connectors/building/review-criteria)). "Tool names must be 64 characters or fewer" (same page). Tool count and description length: not documented. Elicitation on claude.ai: not documented, and an open feature request since 2026-04 ([issue 153](https://github.com/anthropics/claude-ai-mcp/issues/153)). `structuredContent`, `outputSchema`, icons and `title` rendering: not documented for claude.ai. Claude Code supports `list_changed` since 2.1.0, has no fixed per-server tool cap because tool search is on by default, "truncates each tool description and each server's instructions at 2,048 characters by default", supports `structuredContent` since 2.0.21, form and URL elicitation since 2.1.76, resources as `@server:uri` and prompts as `/mcp__server__prompt` ([Claude Code MCP](https://code.claude.com/docs/en/mcp); [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)). The Messages API supports "only tool calls", with per-tool `enabled` and `defer_loading` and a pinned `mcp_tool_listing` under beta `mcp-client-2026-09-15` ([MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)).

Confirmation and safety. claude.ai asks unless a tool is annotated read-only; users may pick "Allow always" and are told to do so only for tools they "trust to run unsupervised" ([get started with custom connectors](https://support.claude.com/en/articles/11175166-get-started-with-custom-connectors-using-remote-mcp)). Enterprise Owners set a per-role, per-connector, per-tool policy of "Always allow", "Needs approval" or "Blocked" ([role-based permissions](https://support.claude.com/en/articles/13930458-set-up-role-based-permissions-on-enterprise-plans)). Claude Code prompts unless a rule `mcp__<server>__<tool>` allows it; an org "ask" policy on a connector tool "prompts on every call ... even in `acceptEdits`, `auto`, and `bypassPermissions`" ([permissions](https://code.claude.com/docs/en/permissions); [Claude Code MCP](https://code.claude.com/docs/en/mcp)). The Messages API never asks; the caller controls the toolset ([MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector)).

Identity. Anthropic says "You may see `"name": "claude-ai"`, `"name": "Anthropic"` (sometimes with a service suffix), or `"name": "claude-code"`" and "Don't gate behavior on an exact `name` or `version` string" ([testing](https://claude.com/docs/connectors/building/testing)). The stable identifiers are the CIMD `client_id` values, `https://claude.ai/oauth/mcp-oauth-client-metadata` and `https://claude.ai/oauth/claude-code-client-metadata`, and the source range `160.79.104.0/21` ([IP addresses](https://platform.claude.com/docs/en/api/ip-addresses)). The User-Agent on MCP calls is not documented; one user saw `Claude-User`, another saw none ([issue 1042](https://github.com/anthropics/claude-ai-mcp/issues/1042); [issue 923](https://github.com/anthropics/claude-ai-mcp/issues/923)).

### ChatGPT

OpenAI renamed most of this area. Custom connectors are now "custom MCP apps" made in Developer mode, and the Apps SDK docs sit under a "Plugins" doc set. Three surfaces matter: custom MCP apps in Developer mode, published apps built with the Apps SDK, and the Responses API `mcp` tool.

Registration. Per user, gated by plan and workspace: "Available to Pro, Plus, Business, Enterprise, and Education accounts on the web", switched on under Settings > Security and login ([developer mode](https://developers.openai.com/api/docs/guides/developer-mode)). "Workspace admins must first enable developer mode from their Admin workspace settings"; on Business only admins can enable it and deploy an app, on Enterprise and Edu RBAC scopes it to a group ([Developer mode and MCP apps](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt)). The help article limits write tools: "Full MCP is only available to Business and Enterprise/Edu users, currently. Pro users can connect MCPs with read/fetch permissions in developer mode" (same page); the developer guide says Pro and Plus get "all tools, both read and write", so the plan rule is unresolved in the sources. The form takes a name, a description, the MCP server URL "including the /mcp path" or a tunnel id, then a "Scan Tools" step and an OAuth prompt if needed ([connect ChatGPT](https://developers.openai.com/plugins/deploy/connect-chatgpt); [Developer mode and MCP apps](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt)). Auth choices are "OAuth, No Authentication, and Mixed Authentication", where static credentials win if given, else CIMD if the AS advertises it and the creator picks it, else DCR ([developer mode](https://developers.openai.com/api/docs/guides/developer-mode)). Exact field labels for client id and secret are not documented. Published apps are workspace-approved: "Only Admins and Owners can publish apps", published apps are a "frozen" snapshot, Enterprise admins choose allowed actions and groups, and on Business "apps cannot be updated after publishing at launch" ([Developer mode and MCP apps](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt)). Public submission needs a verified developer identity and a token at `/.well-known/openai-apps-challenge`; "For private or workspace-only use, use developer mode instead" ([submission](https://developers.openai.com/plugins/deploy/submission); [app review](https://developers.openai.com/plugins/deploy/app-review)). The Responses API takes a per-request tool object with `server_url`, `server_label`, `authorization`, `headers`, `allowed_tools`, `require_approval`, `defer_loading` and `tunnel_id` ([Responses API reference](https://developers.openai.com/api/reference/resources/responses/methods/create)).

Authorization. "Supported clients use Client ID Metadata Documents (CIMD), dynamic client registration (DCR), predefined OAuth clients, and PKCE" ([plugins auth](https://developers.openai.com/plugins/build/auth)). CIMD is preferred; "ChatGPT runs DCR once per MCP server connection, then keeps and reuses the registered OAuth client" (same page). The stable CIMD id is `https://chatgpt.com/oauth/client.json`, used only "For authorization servers that meet the issuer identification requirements"; otherwise ChatGPT uses `https://chatgpt.com/oauth/{callback_id}/client.json` (same page). The live document holds `client_name` `ChatGPT`, `redirect_uris` `["https://chatgpt.com/connector_platform_oauth_redirect"]`, `token_endpoint_auth_methods_supported` `["none","private_key_jwt"]`, `token_endpoint_auth_method` `private_key_jwt`, `jwks_uri` `https://chatgpt.com/oauth/jwks.json` ([client.json](https://chatgpt.com/oauth/client.json)). Redirect URIs: `https://chatgpt.com/connector_platform_oauth_redirect` when the AS returns `iss` per RFC 9207 and sets `authorization_response_iss_parameter_supported: true`, else `https://chatgpt.com/connector/oauth/{callback_id}`; "Copy the exact production redirect URI shown in the MCP server's management page" ([plugins auth](https://developers.openai.com/plugins/build/auth)). PKCE is required: "MCP servers are unsupported when their authorization server metadata omits this field or does not advertise S256" (same page). "Expect ChatGPT to append `resource=https%3A%2F%2Fyour-mcp.example.com` to both the authorization and token requests" (same page). RFC 9728 is required, with `resource` and `authorization_servers` mandatory and `scopes_supported` optional; the same URL may be advertised in `WWW-Authenticate` on `401` (same page). ChatGPT requests OIDC scopes when `scopes_supported` lists them, honours per-tool `securitySchemes`, and needs `offline_access` for refresh (same page; [Developer mode and MCP apps](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt)). No API key path in the ChatGPT UI: "ChatGPT does not support machine-to-machine OAuth grants such as client credentials, service accounts, or JWT bearer assertions, nor can it present custom API keys" ([plugins auth](https://developers.openai.com/plugins/build/auth)). The Responses API does: `authorization` carries a bearer token and `headers` carries arbitrary headers, resent on every request ([Responses API reference](https://developers.openai.com/api/reference/resources/responses/methods/create); [MCP servers guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)). Opaque tokens: not documented either way; the verification text assumes JWT and JWKS ([plugins auth](https://developers.openai.com/plugins/build/auth)). A tool error with `_meta["mcp/www_authenticate"]` triggers the account-linking UI (same page).

Network. "Remote MCP servers can be any server on the public Internet"; a private server needs the Secure MCP Tunnel, which is outbound-only to `api.openai.com:443` and cannot be used for public submission ([MCP servers guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp); [secure MCP tunnels](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels)). Egress ranges are published at `https://openai.com/chatgpt-connectors.json` for "Plugins, connectors, GPT Actions, and agentic commerce"; "Fetch the relevant file regularly and update your allowlist automatically", and "An IP allowlist ... does not replace request authentication" ([IP addresses](https://developers.openai.com/api/docs/guides/ip-addresses)). The file held 278 IPv4 prefixes on 2026-09-22 ([chatgpt-connectors.json](https://openai.com/chatgpt-connectors.json)). ChatGPT also presents an mTLS client certificate with SAN `mtls.prod.connectors.openai.com` chained to the "OpenAI Connectors mTLS intermediate CA" ([plugins auth](https://developers.openai.com/plugins/build/auth)). Egress for the Responses API MCP tool: not documented.

Protocol. No page states the negotiated revision. The docs link the `2025-11-25` auth and annotation schemas, `2025-06-18` for `instructions` and result fields, and `2025-03-26` in the Responses API error section ([plugins auth](https://developers.openai.com/plugins/build/auth); [plugins reference](https://developers.openai.com/plugins/reference); [MCP servers guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)). The handshake is legacy: "MCP servers can also return an instructions field during initialization ... Keep the first 512 characters self-contained" ([plugins MCP server](https://developers.openai.com/plugins/build/mcp-server)). `server/discover` and per-request `_meta`: not documented. Transport: "Supported MCP protocols: SSE and streaming HTTP" in Developer mode ([developer mode](https://developers.openai.com/api/docs/guides/developer-mode)); production apps "must: Support the MCP streamable HTTP transport" ([plugins MCP server](https://developers.openai.com/plugins/build/mcp-server)); the Responses API accepts both ([MCP servers guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)).

Tools. The list is scanned at create time and refreshed by hand: "toggle tools on or off and refresh apps to pull new tools, descriptions, and server instructions" ([developer mode](https://developers.openai.com/api/docs/guides/developer-mode)). Workspace-published apps use a frozen snapshot; "New actions are disabled by default, and changes to existing actions are shown as a diff" ([Developer mode and MCP apps](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt)). `list_changed`: not documented. The Responses API keeps `mcp_list_tools` in context and does not refetch per turn ([MCP servers guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)). No tool count or description limit is documented; the API guide warns that "dozens of tools ... can result in high cost and latency" (same page). Annotations are honoured and required: "We respect the readOnlyHint tool annotation ... Tools without this hint are treated as write actions" ([developer mode](https://developers.openai.com/api/docs/guides/developer-mode)); `readOnlyHint`, `destructiveHint` and `openWorldHint` are marked Required, and "Incorrect or missing action labels are a common cause of rejection" ([plugins reference](https://developers.openai.com/plugins/reference); [submission guidelines](https://developers.openai.com/apps-sdk/app-submission-guidelines)). "Declare outputSchema for any tool that returns structuredContent"; `structuredContent` goes to the model and the widget, `_meta` only to the widget ([plugins reference](https://developers.openai.com/plugins/reference)). Elicitation is form-style only in the text; URL mode is not documented ([plugins MCP server](https://developers.openai.com/plugins/build/mcp-server)). Resources are `ui://` widgets with MIME `text/html;profile=mcp-app` ([troubleshooting](https://developers.openai.com/apps-sdk/deploy/troubleshooting)); prompts are not documented; icons come from the listing, not tool `_meta` ([submission](https://developers.openai.com/plugins/deploy/submission)). `search` and `fetch` are needed only for deep research and company knowledge: "Developer mode does not require search/fetch tools" ([developer mode](https://developers.openai.com/api/docs/guides/developer-mode)).

Confirmation and safety. "Write actions by default require confirmation"; the choice can be remembered per conversation only ([developer mode](https://developers.openai.com/api/docs/guides/developer-mode)). Users and admins pick from "Always ask", "Allow read actions", "Allow low-risk actions" and "Allow all actions"; "Always allow is not offered as a persistent permission to managed-workspace members" ([managing app permissions](https://help.openai.com/en/articles/20001495-managing-app-permissions-in-chatgpt)). Workspace defaults live under Plugin permissions, with per-app override ([admin controls](https://help.openai.com/en/articles/11509118-admin-controls-security-and-compliance-for-plugins-and-apps)). The Responses API asks by default and takes `require_approval` of `"always"`, `"never"` or per-tool lists with a `read_only` filter ([MCP servers guide](https://developers.openai.com/api/docs/guides/tools-connectors-mcp)).

Identity. `clientInfo` and the User-Agent on MCP calls: not documented. The stable identifier is the CIMD `client_id` `https://chatgpt.com/oauth/client.json` with JWKS for `private_key_jwt`, plus the mTLS certificate and the egress list ([plugins auth](https://developers.openai.com/plugins/build/auth)). Tool calls carry `_meta["openai/subject"]` ("Anonymized user id ... for the purposes of rate limiting and identification"), `_meta["openai/session"]`, `_meta["openai/organization"]`, `_meta["openai/locale"]`, `_meta["openai/userLocation"]` and a best-effort `_meta["openai/userAgent"]` that is "not a stable way to detect which host surface is calling" ([plugins reference](https://developers.openai.com/plugins/reference)).

### Microsoft 365 Copilot

Microsoft has three paths. Copilot Studio adds an MCP server as a tool through a wizard that creates a Power Platform custom connector. Microsoft 365 Copilot declarative agents carry an MCP plugin in the app package. The Microsoft 365 admin center registry ("Bring your own MCP server", Agent 365, preview) registers a server tenant-wide behind a gateway. MCP went GA in Copilot Studio on 29 May 2025 ([GA blog](https://www.microsoft.com/en-us/copilot/blog/copilot-studio/model-context-protocol-mcp-is-now-generally-available-in-microsoft-copilot-studio/)) and in declarative agents on 15 December 2025 ([Microsoft 365 developer blog](https://devblogs.microsoft.com/microsoft365dev/build-declarative-agents-for-microsoft-365-copilot-with-mcp/)).

Registration. In Copilot Studio the maker adds the server per agent under Tools > Add a tool > New tool > Model Context Protocol; required fields are "Server name, Server description, and Server URL"; auth is "None", "API key" (header or query, with a parameter name) or "OAuth 2.0" of type "Dynamic discovery", "Dynamic" or "Manual"; Manual takes "Client ID", "Client secret", "Authorization URL", "Token URL template", "Refresh URL" and optional space-separated "Scopes" ([connect to an existing MCP server](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-existing-server-to-agent)). "You must turn on generative orchestration to use MCP" ([extend with MCP](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agent-extend-action-mcp)). Admin control is Power Platform data policy: "if a data policy regulates Power Platform connectors, it also regulates access to the MCP server and its tools" ([connect to an existing MCP server](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-existing-server-to-agent)), and tenant admins classify custom connectors by host URL pattern ([custom connector parity](https://learn.microsoft.com/en-us/power-platform/admin/dlp-custom-connector-parity)). For declarative agents the developer adds the server in Agents Toolkit 6.12+ ("Start with an MCP Server"), picks "OAuth static, OAuth dynamic, Entra SSO, and None", and static prompts for client id, secret and scopes ([build MCP plugins](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/build-mcp-plugins)). The plugin manifest runtime is `"type": "RemoteMCPServer"` with `spec.url` ([plugin manifest 2.4](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-manifest-2.4)); the app manifest `agentConnectors` node takes `mcpServerUrl` (https, max 2048 chars) and an authorization enum of `None`, `OAuthPluginVault`, `ApiKeyPluginVault`, `DynamicClientRegistration`, `AzureKeyVault` ([remoteMcpServer schema](https://learn.microsoft.com/en-us/microsoft-365/extensibility/schema/root-agent-connectors-tool-source-remote-mcp-server)). Agents need admin approval: "each agent must undergo a streamlined process of submission and approval" ([manage agents](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/manage-copilot-agents-integrated-apps)). The BYO registry takes `a365 develop-mcp register-external-mcp-server` with `NoAuth`, `APIKey`, `ExternalOAuth` (pre-registered id, secret, URLs, scopes) or `EntraOAuth`, a server name starting `ext_`, and a declared tool list; an AI admin or Global admin approves and consents, and "Republishing new versions of your remote MCP server isn't currently supported" ([manage tools for agents](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/manage-tools-for-agent); [develop-mcp reference](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/reference/cli/develop-mcp)). End users never add an MCP server themselves; they add a published agent and sign in through the Connection Manager on first use ([connect clients](https://learn.microsoft.com/en-us/power-pages/configure/mcp-connect-clients)).

Authorization. Copilot Studio "Dynamic discovery" is DCR with discovery, "Dynamic" is DCR with hand-typed endpoints, "Manual" is a pre-registered client; the page names no RFC ([connect to an existing MCP server](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-existing-server-to-agent)). The wizard shows a callback URL after Create; the custom connector platform documents the shape by example as `https://global.consent.azure-apim.net/redirect/<connector-id>` ([Entra ID authentication for custom connectors](https://learn.microsoft.com/en-us/connectors/custom-connectors/azure-active-directory-authentication)). No regional consent host list is published. PKCE, `resource` and `WWW-Authenticate` are not documented for Copilot Studio. Generic OAuth on a custom connector sends the token "through the Authorization header" and "client credentials grant type is not supported"; API keys go in a named header or query string ([connection parameters](https://learn.microsoft.com/en-us/connectors/custom-connectors/connection-parameters)). Each tool runs with the user's credentials by default or the maker's ([add tools](https://learn.microsoft.com/en-us/microsoft-copilot-studio/add-tools-custom-agent)). Declarative agents run "OAuth 2.0 authorization code flow, with Proof Key for Code Exchange (PKCE) support enabled by default", accept public clients, and use one fixed redirect for every plugin, `https://teams.microsoft.com/api/platform/v1.0/oAuthRedirect` ([configure OAuth 2.0](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-authentication-oauth)). Entra SSO uses `https://teams.microsoft.com/api/platform/v1.0/oAuthConsentRedirect` and the token store app id `ab3be6b7-f5df-413d-ac2d-abf1e3fd9c0b` ([Entra SSO](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-authentication-entra-sso)); Agents Toolkit fetches tools through `https://vscode.dev/redirect` ([MCP apps](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-mcp-apps)). DCR for declarative agents needs PRM at `.well-known/oauth-protected-resource` and RFC 8414 metadata with a `registration_endpoint`, and has hard limits: "DCR without a client secret isn't supported yet", "DCR isn't available for an MCP server that's protected by Microsoft Entra ID" ([dynamic client registration](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-authentication-dynamic-client-registration)). CIMD, `resource` and `WWW-Authenticate`: not documented for any Microsoft client. API key is "Not supported" for MCP plugins ([plugin authentication](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-authentication)). The BYO registry has no DCR; `ExternalOAuth` is pre-registered and "add the displayed redirect URI to your external IDP application" ([develop-mcp reference](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/reference/cli/develop-mcp)).

Network. The server must be public: "A publicly accessible MCP server endpoint that you can reach from the internet" ([manage tools for agents](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/manage-tools-for-agent)); agent connectors add "Microsoft 365 agents establish long-lived connections to this endpoint" and TLS 1.2+ ([agent connectors](https://learn.microsoft.com/en-us/microsoftteams/platform/m365-apps/agent-connectors)). Copilot Studio calls leave through Power Platform connector infrastructure, so allowlist the `AzureConnectors.<Region>` service tags for every region in the environment's Geo plus the regional `PowerPlatformPlex` tag, and refresh "at least every 90 days" ([connector outbound IP addresses](https://learn.microsoft.com/en-us/connectors/common/outbound-ip-addresses); [Power Platform IP ranges](https://learn.microsoft.com/en-us/power-platform/admin/online-requirements)). Egress ranges for Microsoft 365 Copilot Chat and the Agent 365 gateway: not documented. Custom connectors are on the VNet-supported list, but whether the wizard-made MCP connector honours subnet delegation is not documented ([VNet support](https://learn.microsoft.com/en-us/power-platform/admin/vnet-support-overview)). Cowork asks for "Less than 30 seconds per tool call" ([Cowork plugin development](https://learn.microsoft.com/en-us/microsoft-365/copilot/cowork/cowork-plugin-development)).

Protocol. "Currently, Copilot Studio supports the Streamable transport type" and "Copilot Studio no longer supports SSE for MCP after August 2025" ([connect to an existing MCP server](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-existing-server-to-agent)). The connector wrapper is an OpenAPI 2.0 file with one POST carrying `x-ms-agentic-protocol: mcp-streamable-1.0` (same page; [custom connector FAQ](https://learn.microsoft.com/en-us/connectors/custom-connectors/faq)). No Microsoft page names a revision. The handshake is legacy: Microsoft's own sample says "Copilot Studio handles the MCP protocol (initialize, tools/list, tools/call) natively" and the server can be "stateless: a fresh Server + StreamableHTTPServerTransport is created per request" ([dynamic-mcp-routing sample](https://raw.githubusercontent.com/microsoft/CopilotStudioSamples/main/extensibility/mcp/dynamic-mcp-routing-typescript/README.md)). The newest schema Microsoft cites is `2025-11-25`, on the confirmation page ([confirmation prompts](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-confirmation-prompts)). Cowork documents "Transport: Streamable HTTP" and a `clientInfo` in "the MCP initialize handshake" ([Cowork plugin development](https://learn.microsoft.com/en-us/microsoft-365/copilot/cowork/cowork-plugin-development)). `Mcp-Session-Id` handling and whether SSE-formatted POST responses are accepted: not documented.

Tools. Copilot Studio reads the list from the server and "dynamically reflects these changes" when tools change ([extend with MCP](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agent-extend-action-mcp)); `list_changed` and caching are not documented. Makers toggle tools per server; "When you turn off Allow all, any new tools added to the MCP server are turned off by default" ([add tools and resources from an MCP server](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-components-to-agent)). Hard limits: "the orchestrator can handle a maximum of 128 tools per agent ... we recommend limiting the number of tools in your agent to no more than 25-30" ([add tools](https://learn.microsoft.com/en-us/microsoft-copilot-studio/add-tools-custom-agent)); connector payload 5 MB ([quotas](https://learn.microsoft.com/en-us/microsoft-copilot-studio/requirements-quotas)). Schema pitfalls: "Tools with reference type inputs in the schema are filtered from the list", "Tools with enum type inputs in the schema are interpreted as string", a `type` array truncates the schema, and an integer `exclusiveMinimum` throws ([troubleshooting MCP](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-troubleshooting)). "Copilot Studio currently supports MCP tools and resources"; prompts are not supported; resources arrive only as `resource_link` outputs of a tool ([extend with MCP](https://learn.microsoft.com/en-us/microsoft-copilot-studio/agent-extend-action-mcp); [add tools and resources](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-components-to-agent)). Annotations, `structuredContent`, `outputSchema`, elicitation, `title` and icons: not documented for Copilot Studio. Declarative agents resolve tools "At runtime, per session" with dynamic discovery, run "runtime responsible AI (RAI) and cross-prompt injection attack (XPIA) validation" on each new or changed tool, and let the server "return a tool list tailored to the signed-in user" ([dynamic tool discovery](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-dynamic-tool-discovery)). Manifest strings "SHOULD be limited to 4K characters" and `description_for_model` past 2048 "MAY be ignored" ([plugin manifest 2.4](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-manifest-2.4)). `readOnlyHint` is honoured; for MCP apps `destructiveHint`, `openWorldHint` and `idempotentHint` are marked not supported and `title` appears in the sample payload ([MCP apps](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-mcp-apps)). Cowork reads `readOnlyHint`, `destructiveHint` and `title`; "Tools without annotations are treated as destructive and require confirmation" ([Cowork plugin development](https://learn.microsoft.com/en-us/microsoft-365/copilot/cowork/cowork-plugin-development)). The BYO registry freezes a "Tools Snapshot"; "Tool names must exactly match the names exposed by the remote MCP server" ([manage tools for agents](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/manage-tools-for-agent)).

Confirmation and safety. Copilot Studio has a per-tool "Ask the end user before running" switch, "set to No by default" ([add tools](https://learn.microsoft.com/en-us/microsoft-copilot-studio/add-tools-custom-agent)); an "Always allow" option and any use of annotations to decide are not documented. DLP blocks are real time: "Blocking Power Platform connectors also blocks access to tools in connected MCP servers" ([data policies for agents](https://learn.microsoft.com/en-us/microsoft-copilot-studio/admin-data-loss-prevention)). Microsoft 365 Copilot asks once on first use, then "all future operations that retrieve data ... don't require any confirmation. Other HTTP operations prompt the user"; an MCP tool with `readOnlyHint: true` skips the prompt ([confirmation prompts](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-confirmation-prompts)). "Always Allow" appears only when the manifest sets `isNonConsequential: true` ([plugin manifest 2.4](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-manifest-2.4)). Cowork: "Confirmation is required if readOnlyHint == false or destructiveHint == true" ([Cowork plugin development](https://learn.microsoft.com/en-us/microsoft-365/copilot/cowork/cowork-plugin-development)). BYO servers are approved or blocked by the admin; "Blocked MCP servers can't be invoked at runtime across any client surface" ([manage tools for agents](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/manage-tools-for-agent)).

Identity. Only Cowork documents its identity: User-Agent `copilot-cowork/1.0` on every request and `clientInfo` `{ "name": "copilot-cowork", "version": "<version>" }` on `initialize`; "Match the copilot-cowork prefix, case-insensitive"; the identity "never carries user identity" ([Cowork plugin development](https://learn.microsoft.com/en-us/microsoft-365/copilot/cowork/cowork-plugin-development)). Copilot Studio and Copilot Chat `clientInfo` and User-Agent: not documented. A custom connector back end may see `x-ms-workflow-name`, `x-ms-environment-id`, `x-ms-workflow-version` and `x-ms-workflow-run-id`, "subject to change", and whether the MCP path sends them is not documented ([custom connector FAQ](https://learn.microsoft.com/en-us/connectors/custom-connectors/faq)). With Entra SSO the token's client is `ab3be6b7-f5df-413d-ac2d-abf1e3fd9c0b` ([Entra SSO](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-authentication-entra-sso)). Since July 2026 every new Copilot Studio agent gets a Microsoft Entra Agent ID ([what's new](https://learn.microsoft.com/en-us/microsoft-copilot-studio/whats-new)). Tenant-side audit exists in Purview and in Defender hunting (`ExecuteToolByGateway`), but the gateway adds no documented headers for the server ([dynamic tool discovery](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-dynamic-tool-discovery); [manage tools for agents](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/manage-tools-for-agent)).

### Consequences for the server

- Serve both protocol eras on one endpoint. Claude already sends `server/discover` and `2026-07-28` per-request `_meta` (user reports on Anthropic's tracker; [issue 1027](https://github.com/anthropics/claude-ai-mcp/issues/1027)), while ChatGPT and every Microsoft client still open with `initialize` ([plugins MCP server](https://developers.openai.com/plugins/build/mcp-server); [dynamic-mcp-routing sample](https://raw.githubusercontent.com/microsoft/CopilotStudioSamples/main/extensibility/mcp/dynamic-mcp-routing-typescript/README.md)). The spec's dual-era server answers both on the same URL ([versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)). Do not add an `/sse` endpoint: Copilot Studio dropped SSE ([connect to an existing MCP server](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-existing-server-to-agent)), Claude Code falls back on its own ([Claude Code MCP](https://code.claude.com/docs/en/mcp)), and ChatGPT accepts Streamable HTTP ([developer mode](https://developers.openai.com/api/docs/guides/developer-mode)).
- Support all three client registration methods in better-auth. CIMD for Claude and ChatGPT, DCR as the fallback both of them use and the only automatic path Microsoft has, and a pre-registered client for Copilot Studio "Manual", Agents Toolkit "OAuth static", the BYO registry's `ExternalOAuth`, Claude's "Use your own OAuth client" and ChatGPT's static credentials. The AS metadata must carry `client_id_metadata_document_supported: true` and `none` in `token_endpoint_auth_methods_supported`, or Claude silently drops to DCR ([authentication](https://claude.com/docs/connectors/building/authentication)). DCR must return a `client_secret`, because "DCR without a client secret isn't supported yet" for Microsoft 365 Copilot ([dynamic client registration](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-authentication-dynamic-client-registration)). The spec deprecates DCR ([changelog](https://modelcontextprotocol.io/specification/latest/changelog)), so this is a compatibility switch, not the default.
- Give admins an OAuth client screen in OpenLaw. Every Microsoft path and both vendors' "own client" options need a deployer to create a client id and secret and paste the vendor's redirect URI. That screen is where the allowlist below lives.
- Allowlist these redirect URIs: `https://claude.ai/api/mcp/auth_callback` ([authentication](https://claude.com/docs/connectors/building/authentication)); `http://localhost/callback` and `http://127.0.0.1/callback` with the port ignored for Claude Code (same page); `https://chatgpt.com/connector_platform_oauth_redirect` and `https://chatgpt.com/connector/oauth/{callback_id}` ([plugins auth](https://developers.openai.com/plugins/build/auth)); `https://teams.microsoft.com/api/platform/v1.0/oAuthRedirect` ([configure OAuth 2.0](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-authentication-oauth)); `https://vscode.dev/redirect` for Agents Toolkit ([MCP apps](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-mcp-apps)); and the per-connector `https://global.consent.azure-apim.net/redirect/<id>` that Copilot Studio shows after Create, which the deployer pastes in ([Entra ID authentication for custom connectors](https://learn.microsoft.com/en-us/connectors/custom-connectors/azure-active-directory-authentication)).
- Advertise `S256` in `code_challenge_methods_supported` and return `iss` with `authorization_response_iss_parameter_supported: true`. ChatGPT refuses a server without S256 and gives the stable redirect only with `iss` ([plugins auth](https://developers.openai.com/plugins/build/auth)); Claude Code fails a sign-in with an unexpected issuer ([Claude Code MCP](https://code.claude.com/docs/en/mcp)).
- Validate token audience but do not require the `resource` parameter at the AS. Claude and ChatGPT send it ([troubleshooting](https://claude.com/docs/connectors/building/troubleshooting); [plugins auth](https://developers.openai.com/plugins/build/auth)); no Microsoft page mentions it, so a Copilot Studio token request may arrive without one and the AS must still issue a token whose audience is the MCP URL.
- Publish PRM at `/.well-known/oauth-protected-resource` and at the path-suffixed form, return `WWW-Authenticate: Bearer resource_metadata="..." scope="..."` on `401` and `error="insufficient_scope"` on `403`, and expose RFC 8414 metadata with a `registration_endpoint`. Claude reads the header only on `401` and probes the path form first ([authentication](https://claude.com/docs/connectors/building/authentication)); ChatGPT requires PRM with `authorization_servers` ([plugins auth](https://developers.openai.com/plugins/build/auth)); Microsoft's DCR needs `registration_endpoint` in `/.well-known/oauth-authorization-server` ([dynamic client registration](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-authentication-dynamic-client-registration)). List `offline_access` in `scopes_supported` on the AS so Claude and ChatGPT ask for refresh tokens ([lazy authentication](https://claude.com/docs/connectors/building/lazy-authentication); [plugins auth](https://developers.openai.com/plugins/build/auth)). Keep discovery and token endpoints under 10 seconds ([authentication](https://claude.com/docs/connectors/building/authentication)).
- Accept API keys on the same URL as `Authorization: Bearer <key>` and as a named header such as `x-api-key`. Claude Code, the Messages API, the Responses API, Copilot Studio's "API key" type and the BYO registry all send a static header ([Claude Code MCP](https://code.claude.com/docs/en/mcp); [MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector); [Responses API reference](https://developers.openai.com/api/reference/resources/responses/methods/create); [connect to an existing MCP server](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-existing-server-to-agent); [develop-mcp reference](https://learn.microsoft.com/en-us/microsoft-agent-365/developer/reference/cli/develop-mcp)). The ChatGPT UI and Microsoft 365 MCP plugins cannot, so OAuth stays mandatory ([plugins auth](https://developers.openai.com/plugins/build/auth); [plugin authentication](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-authentication)).
- Run on a public IPv4 HTTPS host with no cross-host redirects, and document three allowlists for deployers: Anthropic `160.79.104.0/21` ([IP addresses](https://platform.claude.com/docs/en/api/ip-addresses)), OpenAI `chatgpt-connectors.json` refreshed on a schedule ([IP addresses](https://developers.openai.com/api/docs/guides/ip-addresses)), and the `AzureConnectors.<Region>` plus `PowerPlatformPlex` service tags for the tenant's Geo ([connector outbound IP addresses](https://learn.microsoft.com/en-us/connectors/common/outbound-ip-addresses)). Verifying ChatGPT's mTLS certificate is optional extra proof ([plugins auth](https://developers.openai.com/plugins/build/auth)).
- Keep the default toolset at 25 to 30 tools and never above 128, with names of 64 characters or fewer and descriptions under 2,048 characters, and put the point of the server in the first 512 characters of `instructions` ([add tools](https://learn.microsoft.com/en-us/microsoft-copilot-studio/add-tools-custom-agent); [review criteria](https://claude.com/docs/connectors/building/review-criteria); [Claude Code MCP](https://code.claude.com/docs/en/mcp); [plugins MCP server](https://developers.openai.com/plugins/build/mcp-server)). Avoid `$ref`, `type` arrays and integer `exclusiveMinimum` in input schemas, and do not rely on `enum`, or Copilot Studio drops or mangles the tool ([troubleshooting MCP](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-troubleshooting)). Return the list in a fixed order ([changelog](https://modelcontextprotocol.io/specification/latest/changelog)).
- Annotate every tool with `title`, `readOnlyHint` and `destructiveHint`. A missing hint means "write" in ChatGPT ([developer mode](https://developers.openai.com/api/docs/guides/developer-mode)), "destructive" in Cowork ([Cowork plugin development](https://learn.microsoft.com/en-us/microsoft-365/copilot/cowork/cowork-plugin-development)), a per-call prompt in Claude ([review criteria](https://claude.com/docs/connectors/building/review-criteria)) and a prompt on every non-read call in Copilot Chat ([confirmation prompts](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-confirmation-prompts)). Return `structuredContent` with an `outputSchema` and a text `content` item too, because ChatGPT wants the pair and Copilot Studio only documents text and `resource_link` ([plugins reference](https://developers.openai.com/plugins/reference); [add tools and resources](https://learn.microsoft.com/en-us/microsoft-copilot-studio/mcp-add-components-to-agent)).
- Treat tool names as a public contract and keep tool calls under 30 seconds. ChatGPT freezes published apps and turns new tools off by default ([Developer mode and MCP apps](https://help.openai.com/en/articles/12584461-developer-mode-and-mcp-apps-in-chatgpt)), the BYO registry pins a tool snapshot and cannot republish ([manage tools for agents](https://learn.microsoft.com/en-us/microsoft-365/admin/manage/manage-tools-for-agent)), and Cowork asks for under 30 seconds per call ([Cowork plugin development](https://learn.microsoft.com/en-us/microsoft-365/copilot/cowork/cowork-plugin-development)). Do not depend on elicitation for anything a user must do; only Claude Code documents both modes ([Claude Code MCP](https://code.claude.com/docs/en/mcp)), ChatGPT documents form mode ([plugins MCP server](https://developers.openai.com/plugins/build/mcp-server)), claude.ai and Microsoft document none. Use a `401` or a tool error with `_meta["mcp/www_authenticate"]` to send the user back to sign-in ([plugins auth](https://developers.openai.com/plugins/build/auth); [Entra SSO](https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-authentication-entra-sso)).
- Name the client in the audit log from the OAuth `client_id` or API key id first, then `clientInfo`, then the source range. The CIMD URLs are stable ([CIMD document](https://claude.ai/oauth/mcp-oauth-client-metadata); [client.json](https://chatgpt.com/oauth/client.json)); `clientInfo` names vary and Anthropic says not to gate on them ([testing](https://claude.com/docs/connectors/building/testing)); ChatGPT adds `_meta["openai/subject"]` and `_meta["openai/session"]` per call ([plugins reference](https://developers.openai.com/plugins/reference)); Copilot Studio sends nothing documented. This extends the actor-attribution bullet in section 8.

## 11. Can a chat client hand a file to a tool? (checked 2026-09-23)

Question raised in Round 5 on `openlaw_document_upload`. Primary sources only.

### The spec

- The 2026-07-28 revision adds no file or binary tool input. `tools/call` arguments stay plain JSON. Binary content exists only from server to client (blob resources, image and audio results). https://modelcontextprotocol.io/specification/2026-07-28/changelog
- The File Uploads working group charter (2026-04-23) says servers that need a file today "resort to prose instructions asking for base64 strings or local paths". https://modelcontextprotocol.io/community/working-groups/file-uploads
- SEP-2356 (declarative file inputs) was closed unmerged on 2026-06-26 in favour of SEP-2631 (file objects, `files/authorizeUpload`, `files/authorizeDownload`). SEP-2631 is an open draft, last updated 2026-09-17, and is in no published revision. https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2631
- Streamable HTTP documents no message size limit.

### Claude

- The connector spec lists tools, prompts and resources, text and image results, and no file input. Result limit about 150,000 characters and a 240 second timeout in claude.ai and desktop; 25,000 tokens in Claude Code. No input size is documented. https://claude.com/docs/connectors/building
- A chat upload gives the model extracted text only (plus visual analysis for PDFs under 100 pages). The upload article says nothing about passing a file to a connector. https://support.claude.com/en/articles/8241126-upload-files-to-claude
- The Notion connector has no upload tool. Notion's own MCP returns a temporary upload URL and the bytes go by a separate PUT. Whether claude.ai can complete that PUT is not documented. https://claude.com/connectors/notion
- Claude Code can read local files, but the model must emit every base64 character as tool-call tokens. Programmatic tool calling is not available in Claude Code. https://code.claude.com/docs/en/mcp

### ChatGPT

- The Apps SDK is the only documented path, and it is the reverse shape. A tool declares `_meta["openai/fileParams"]` and ChatGPT sends `{download_url, file_id, mime_type, file_name}`. The server downloads the bytes. No base64 in arguments. Size and MIME limits are not documented. https://developers.openai.com/apps-sdk/reference
- A published app in OpenAI's own examples repo reports composer attachments arrive through `fileParams` about 90 percent of the time (open issue #237).
- Whether unpublished developer-mode connectors get `fileParams` is not documented.

### Microsoft 365 Copilot

- Copilot Studio agents accept a 15 MB file on the Microsoft 365 Copilot channel and read up to 30,000 characters of text. https://learn.microsoft.com/en-us/microsoft-copilot-studio/image-input-analysis
- Raw bytes reach a tool only through a Power Fx formula bound to a connector or flow input. It does not work with "Dynamically fill with AI". MCP tools have no Inputs section, so an attachment cannot be bound to an MCP argument. https://learn.microsoft.com/en-us/microsoft-copilot-studio/guidance/pass-files-to-connectors
- Microsoft's own Dynamics MCP confirms the pattern: upload is not in the MCP server; a flow tool takes the bytes. https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/copilot/mcp/mcp-attachments
- Declarative agents do not support uploaded files; Word interaction passes document text. Custom engine agents do not support attachments.

### What this means for `openlaw_document_upload`

A base64 argument works only for a headless Client (a script) and, at a token cost, for Claude Code. No chat client can put the bytes of an attached file into an MCP tool argument today. ChatGPT can deliver a download URL if the tool declares `openai/fileParams`. Copilot cannot reach an MCP tool with a file at all. The spec-level answer (SEP-2631) is a draft. Confidence: high on the spec and Copilot, medium on Claude (docs are silent, not negative), medium on ChatGPT composer attachments.
