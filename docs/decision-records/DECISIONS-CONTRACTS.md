Decisions specific to the Contracts (CLM) module. Platform-level decisions that apply across all modules (data model, role model, intake, activity tracking, etc.) live in `DECISIONS.md` and are referenced by ID where relevant.

## Format

Each decision is structured as:

- **Status** — Accepted / Superseded by #N
- **Date** — when accepted
- **Context** — what question is being answered, what constraints exist
- **Decision** — what was decided
- **Rationale** — why
- **Alternatives considered** — what was not chosen, briefly
- **Consequences** — what this commits us to downstream

Decisions are numbered `CTR-###`.

## CTR-001 — Lifecycle: fixed six-stage backbone + configurable statuses

- **Status** — Accepted
- **Date** — 2026-08-02
- **Context** — Contracts need a lifecycle model. The contract-details mocks show both a "Status" pill (C.5) and a "Stage" field (D.8) — a duplication that must resolve to one stored field. Unlike matters (MTR-002's two categories), contract code genuinely branches at more points: approval rules gate before signature, the e-signature integration fires during signature, term/renewal logic runs only on executed contracts, and ended contracts drop from active surfaces. Per the configurable-over-fixed default and its carve-out (fixed enums only where code branches — DD-013/DD-016 precedent).
- **Decision** — Two-layer model, MTR-002 scaled up:
  - **Fixed system stages** (code branches on these; immutable enum): `draft` → `review` → `approval` → `signature` → `active` → `ended`.
  - **Configurable statuses** (`contract_statuses`, same machinery as `matter_statuses`): each status maps to exactly one stage, mapping immutable after creation. Seeds: Draft (draft); Internal review, Redlining with counterparty (review); Awaiting approval (approval); Out for signature (signature); Active (active); Expired, Terminated (ended).
  - Contract stores `status_id` only; **stage is derived** from the status. The status pill shows the status label; the pipeline/progress visualization shows the stage. C.5 and D.8 are the same datum at two zoom levels.
  - Stage order is the canonical forward sequence but transitions are **not restricted** — a contract can move to any status (deals collapse, redlines reopen after approval). Stage regression is allowed and logged per DD-017.
  - Same guardrails as MTR-002: ≥1 unarchived status per stage that has seeds; seed rows for `draft`, `active`, and one `ended` status are system-protected; global list, not per-type.
- **Rationale** — The stage backbone gives approvals, e-sign, renewals, and surfaces a stable enum to branch on without hardcoding labels teams will want to rename. Matches the market-leader pipeline shape (Ironclad/LinkSquares). Deriving stage from status kills the stage-vs-status duplication in the mocks.
- **Alternatives considered** — Three coarse categories (pre_execution/active/ended): approval and e-sign gates would need separate per-contract flags. Fully fixed status enum: contradicts the configurable default; teams rename these labels. Enforced forward-only transitions: real deals move backwards; a transition matrix adds config surface with no v1 payoff.
- **Consequences** — `contract_statuses` table + `contracts.status_id` in SCHEMA.md. Settings surface: Contracts → Statuses (sibling of Matters → Statuses). Approval (Q8) and e-signature (Q9) decisions can key off `approval`/`signature` stages. Renewal logic (Q4) keys off `active`/`ended`. Grill-plan rows C.5/D.8 unblocked; H.C4 unblocked by **CTR-012**'s accepted approval model.

## CTR-006 — Term & renewal model: typed columns, derived notice deadline, notify-only engine

- **Status** — Accepted
- **Date** — 2026-08-02
- **Context** — The term/renewal model gates eight blocked screen rows (G.R3, G.R5–R7, I.B2–B5, I.B7) and is the reason small legal teams buy CLM (missed auto-renewals). Also the designated revisit for the derived-dates question deferred in the Matters grill.
- **Decision** —
  - **Storage (typed columns on `contracts`)**: `term_type` (`fixed | auto_renew | evergreen`; code branches on this — expiry behavior, renewal engine, calendar surfaces), `effective_date` (nullable until known), `expiry_date` (null for evergreen), `renewal_period_months` (auto_renew only), `notice_period_days` (nullable).
  - **Derived, never stored**: notice deadline = `expiry_date − notice_period_days`. Surfaces on the renewal calendar and reminders. (Derived dates accepted here — this is the case that earns them.)
  - **Engine is notify-only, never auto-advance** (user override of the auto-advance recommendation): reminders fire at the notice deadline and at expiry; when an auto-renew contract passes its renewal date un-actioned, the record shows a "renewal pending confirmation" state — a human confirms, and only then does `expiry_date` advance (activity-logged per DD-017). The system never mutates term data on its own.
  - Population of these fields can be manual or via AI analysis (CTR-008).
- **Rationale** — Typed columns are required for the engine and calendar to branch; free-text terms can't drive reminders. Notify-only keeps humans the sole writers of legal-state data — Blair prefers the record to await confirmation over the system asserting a renewal happened.
- **Alternatives considered** — Dates-only (no term_type/notice machinery): defers the core CLM value. Term-ledger table (per-term rows): second entity; activity log already preserves history. Auto-advance on renewal date: recommended, declined — record must never change without a human.
- **Implementation note (2026-08-17, M16/1)** — The five columns landed in migration `0046_contract_term`. Existing rows took `fixed` — an assertion about them, not a discovery. The two shape rules are database checks and seam refusals both, each refusal carrying its own RFC 9457 type (TECH-020): an `evergreen` contract holds no expiry, and only an `auto_renew` one holds a renewal period. A term-type change clears what the new type cannot hold. Each clear is activity-logged as the edit it is. The notice deadline and days remaining are computed where the answer is assembled and stored nowhere. The surfaces that draw the deadline are M16's later slices. Record anatomy: **DES-040**.
- **Implementation note (2026-08-17, M16/2)** — The Overview gained the Term timeline card. It draws the record and nothing else: the periods are the ones the stored dates imply, walked back from the expiry a renewal period at a time, and the notice deadline is the one the read already answers. Nothing about the picture is stored, so a date edited on the Contract card moves the mark below it. A bar per **confirmed** roll (grill rows I.B3–I.B5) waits for the slice that writes the log entry — this card cannot draw a roll the record cannot prove. Card anatomy: **DES-041**.
- **Implementation note (2026-08-17, M16/4)** — The pending state and the confirmed roll landed together, and neither added a column. **"Renewal pending confirmation" is a predicate**: an auto-renewing, unarchived contract whose expiry has passed. It rides the record's row beside the other derivations, so it appears because a read says so and clears the moment the expiry advances or the term is re-typed. Nothing computes it on a schedule, because nothing in this milestone runs on one. **The confirmed roll is the record's one renewal act so far** (CTR-007's first vehicle): the request carries the expiry it was raised against and the expiry to advance to, and the seam compares the first under the contract's row lock — which is what makes two confirms racing for one roll advance the term **exactly once**, the loser refused by its own RFC 9457 type rather than rolling the term a second time. The record proposes the second date (the current expiry plus the renewal period, clamped at a month's end) and the person may enter another, because a roll whose dates shifted in negotiation is recorded as it really landed. The status and the stage are untouched throughout. **Nothing stores a renewal**: the `contract.renewal_confirmed` entry is the whole record of one, and both the confirmed-renewal rows on the Approvals & signing card and the record's "Last renewal" fact are that log read back — the grill's G.R5 resolution, discharged. Banner, dialog, and row anatomy: **DES-043**.
- **Consequences** — Five columns in SCHEMA.md. A "pending confirmation" indicator state exists in the UI (contract remains `active` stage; this is a banner/derived state, not a status). Unconfirmed lapses mean the record can show a past expiry on a legally-renewed contract — accepted trade-off. Renewal calendar + reminder surfaces are committed (notifications feature DD to specify delivery). Grill-plan G.R3, G.R5–R7, I.B2–B5, I.B7 unblocked.

## CTR-007 — Renewal routing: user's choice of vehicle

- **Status** — Accepted
- **Date** — 2026-08-02
- **Context** — When a contract renews (beyond a confirmed same-paper roll), what record represents the new term? Recommended same-record-rolls / renegotiation-= new-contract; Blair widened it: "It should be up to the user. They could theoretically add the renewal as an amendment, child contract, or as a new contract."
- **Decision** — No forced renewal shape. Four supported routes, chosen by the user at renewal time:
  1. **Confirm the roll** — same record, expiry advances (the CTR-006 confirmation flow); for unchanged auto-renewals.
  2. **Amendment** — renewal papered as an amendment on the existing contract (amendment model in the Q11 relations decision).
  3. **Child contract** — new record parented to the original.
  4. **New contract** — standalone successor, linked to the predecessor.
- **Rationale** — Teams paper renewals differently per relationship; the tool records what happened rather than imposing a doctrine. Consistent with MTR-015's no-forced-semantics stance.
- **Alternatives considered** — Same-record always / successor-record always: both impose one doctrine on heterogeneous practice.
- **Implementation note (2026-08-17, M16/5)** — **The other three vehicles landed, and the dialog became the chooser the C9 mock always drew.** Confirming the roll writes on the record (M16/4); the other three route, and routing rather than writing is what they are. **Amendment** hands the person to the record's own Documents section with the version composer open on the primary chain and the kind already `amendment` — the M11 write path untouched, no new record, and no link, because the renewal stays on the record it amends. **Child contract** and **new contract** open the _existing_ create dialog, prefilled, and the record is born linked: the child on `contracts.parent_id`, the successor on a CTR-015 `renews` row pointing at its predecessor. One direction only — a successor renews its predecessor, and there is no mirror row. **The prefill is a list, and the list is the decision**: our entity, the value, the term shape, and the counterparties are copied, because they are facts about the _deal_; the status, the team, the Owner, priority, risk, and the Confidential flag are never copied, because they are facts about a _record_ — CTR-015's no-inheritance stance, applied at birth. **The split of who copies what follows what the dialog draws.** The title and the type are the two fields the create dialog has, so they are seeded there and stay editable until the button is pressed; everything else is copied by the create seam, which is the only place that could copy it and the only place worth asserting it at. The amendment option is **absent**, never disabled, on a record with no primary document: a chain that does not exist has nothing to append (DES-035 clause 9). Dialog and prefill anatomy: **DES-044**.
- **Consequences** — The Q11 relations model must support amendment and parent/child/renewal link types (pulled forward as the enabler). Renewal reporting must tolerate all four shapes (a renewal is identified by the link/log, not by record shape).

## CTR-009 — Key dates: contract_key_dates, MTR-004 sibling

- **Status** — Accepted
- **Date** — 2026-08-02
- **Context** — CTR-006's typed term dates cover expiry/notice; contracts also carry ad-hoc dates (price reviews, delivery milestones, option-exercise windows, warranty expiry).
- **Decision** — `contract_key_dates` table, same shape as `matter_key_dates` (date, label, note). Typed term dates stay in their columns; key dates are the free-form escape hatch. Deadline surfaces show the union of term-derived dates and key dates; earliest upcoming = "next deadline".
- **Rationale** — Custom date fields are per-type and single-valued — awkward for N ad-hoc dates on one contract. Same machinery as matters keeps surfaces uniform.
- **Alternatives considered** — Term dates only (custom fields as overflow): single-valued limitation. Typed milestone table: over-modeled.
- **Implementation note (2026-08-17, M16/3)** — `contract_key_dates` landed in migration `0047_contract_key_dates` with the three columns and nothing more. The open question the matters grill left is answered by the strip rather than the adoption: **no owner on a key date**, and **no per-date reminder schedule** — NOT-004's one global offset list already covers every tracked date, and what fires on them is M18's. The union is the seam's answer rather than a merge any surface does: one read returns the key dates, the expiry, and the derived notice deadline in one ordered list, with what is still ahead nearest-first, what has gone by after it, a day count on every entry, and exactly one entry marked as the next deadline. Two of the three sources carry no row id, which is what says they are read there and edited on the record's own term. Add, edit, and remove are three closed-union activity actions at the record tier; a removal's entry carries the label and the date, because the row is gone and the entry is what is left of it. Nothing here holds an audience: reach is the owning contract's, so DD-014 composes with no rule of its own. Section anatomy: **DES-042**.
- **Consequences** — Table in SCHEMA.md. Contract deadline surfaces aggregate three sources: derived notice deadline, expiry, key dates.

## CTR-012 — Approvals: manual approvers + reusable approver groups, parallel, soft gate

- **Status** — Accepted
- **Date** — 2026-08-02
- **Context** — When/who/how of contract approval; gates the events card's Decision column (H.C4). Recommended a threshold rule engine; Blair chose a lighter shape: "The user can add manual approvers at approval stage and also set up custom approver groups (templates)."
- **Decision** —
  - **No auto-firing rule engine.** At the approval stage the contract owner adds approvers **manually** — individually and/or by applying a named **approver group**.
  - **Approver groups** are admin-managed templates (Settings → Contracts → Approver Groups): name + member list (e.g. "Commercial sign-off" = GC + CFO). Applying a group **snapshots** its members into approval requests at apply time — later group edits don't touch existing requests.
  - **Parallel**: all pending approvers must approve; no sequential chains in v1.
  - Recorded in `contract_approvals`: approver, source (`manual|group` + group ref), status (`pending|approved|rejected`), note, decided_at, requested_by. This is the datum H.C4 renders.
  - **Soft gate** (recommended, accepted): advancing past approval with pending/rejected approvals warns loudly, is allowed, and is activity-logged as an override — consistent with CTR-001's unrestricted transitions and the signal-not-lock philosophy (MTR-008).
- **Rationale** — Groups capture the recurring 80% ("this is a commercial contract → apply Commercial sign-off") without a rules engine's config surface; in a 2–10 person team the policy holder and the overrider are often the same person.
- **Alternatives considered** — Threshold rule list (recommended, declined — parked to FUTURE-FEATURES as a natural later layer that would _pre-apply_ groups). Ad-hoc only: loses reusable templates. Sequential workflow builder: big-team territory. Hard gate: blocks legitimate small-team situations.
- **Consequences** — `approver_groups`, `approver_group_members`, `contract_approvals` in SCHEMA.md. Settings surface added. Grill-plan H.C4 unblocked (Decision column = approval outcomes). Approval-stage UI needs an "apply group" affordance.
- **Addendum (2026-08-21, [#391](https://github.com/juggernog20/OpenLaw/issues/391)) — two live approver groups may not share a name.** The decision above says a group is a name and a member list, and it says nothing about the name being unique. Nothing in the schema said so either, so an install could hold two groups called "Commercial sign-off" — and the apply picker would draw them as two identical entries, because this table has no slug and no display order and the name is therefore its whole identity. The API review found the gap; the answer is a unique index rather than a note that duplicates are accepted.

  **The rule is the one the rest of the schema already keeps.** A folder's siblings, a person's saved views, and a user's email address are all unique on `lower(name)` — case-insensitive, because that is the reading the sort takes (DES-033) and because two names that read as the same word are the same name to the Administrator choosing between them. This is that rule, applied to the one list that had been left out.

  **It binds the live rows only, so archiving frees the name.** The index is partial on `archived_at is null`. SET-003's soft delete takes an archived group out of the apply picker and out of the default list, and applying a group has already snapshotted its members into the requests that used it — so an archived row's name is read by nobody and has nothing left to collide with. The one clash this leaves is a **restore** onto a name a live group has taken since; it is refused 409 with its own sentence, because nothing is wrong with the archived group and the fix is on the other one.

  **Existing rows are renamed, not refused.** An install can really be carrying a pair, so migration `0065` resolves it before the index is created: within a set of live rows that read as the same name the **oldest keeps it**, ordered by `(created_at, id)`, and every later one takes the first free " (2)", " (3)" suffix. Refusing the upgrade — 0060's answer for an account with no resolvable issuer — is the wrong answer here, because a duplicate name is a cosmetic clash between two rows that both work, and an unresolvable account was nobody able to sign in. A rename here reaches nothing but the picker's label, for this decision's own reason: applying a group snapshots its members, so no request that already exists reads this column. What the migration cannot do is write an activity entry, because it has no actor; it raises a NOTICE naming every rename instead, into the container-start log the operator is already watching.

- **Addendum (2026-08-16, M15/1)** — The adapter seam landed as `SigningProvider` in the API's lib layer, on the storage-adapter and doc-engine precedents: one narrow interface, a terminal/transient error split, the DocuSign driver, a deterministic fake, and one shared contract suite both run. - **Addendum (2026-08-16, M15/2)** — The **send** landed on the record. A Member+ user with reach to a contract picks a version of its **primary document**, names the signers as name-and-email pairs, and sends through the stored connector; loose attachments are not sendable, because the executed copy comes back to the chain the send left from (CTR-014). Every signer is asked **in parallel** — there is no routing order in v1, and the stored order is only the order they were typed. `contract_envelopes` and `contract_envelope_signers` hold it, with **at most one live envelope per contract** kept by a partial unique index on the `sent` status. The provider is called first and the row commits once it accepts; an envelope the provider took but the record could not keep is **voided again** before the refusal is raised, so the two systems do not drift apart silently. The two refusals a client branches on — no connector configured, and an envelope already out — carry RFC 9457 problem types in `@openlaw/shared` (TECH-020), and the record uses them to leave the send control **absent** rather than disabled. The record's card takes its reserved two-part name, **"Approvals & signing"**, and the envelope's anatomy is **DES-036**.
- **Addendum (2026-08-16, M15/3)** — The **status comes back**. DocuSign Connect pushes an envelope's fate to `POST /api/v1/signing/:provider/webhook`, this install's first unauthenticated inbound write path. It is an **encapsulated Fastify plugin** on the better-auth handler's precedent, with its own raw-buffer content-type parser, because verification is an HMAC over the exact bytes delivered and a re-serialized body would not verify. Three rules make it safe to leave open: a delivery that does not verify against the stored Connect secret is **refused 401**, and so is a malformed one and one arriving at an install with no connector — one sentence for all three, because telling them apart would tell an attacker too; a delivery naming an envelope this install does not hold is **acknowledged, not refused**, so our own log does not become the provider's retry queue; and the change is applied through **one idempotent status-transition function** (`lib/signing/transitions.ts`), which locks the envelope row, refuses to move an envelope that has already ended, and writes the row and its activity entry in one transaction. That function is the single funnel every status feed goes through — this webhook, the reconciliation sweep, and the void — which is what lets them run together: a transition already applied is a no-op. A decline or a void keeps the reason it ended with, bounded at `MAX_ENVELOPE_REASON_LENGTH`; every ended envelope — signed, declined, or voided — keeps the moment it ended, defaulted to the moment we were told when the provider names none. Each ending is narrated as its own entry at the standing record tier with **no actor**, which is how the feed says the integration spoke rather than a person. The row's ending cells and the mock's webhook note are **DES-037**.
- **Addendum (2026-08-16, M15/4)** — The **void** landed on the record. A live envelope is withdrawn from its row on the "Approvals & signing" card by the **approvals-cancellation audience**: the person who sent it, the contract's Owner, or an Administrator (`POST /api/v1/envelopes/:envelopeId/void`). Anybody else is refused **403** at the seam and is drawn **no control at all**, the DES-035 clause 9 absence rule. The **reason is required** — the provider records it with the withdrawal and the row draws it under the status pill, so a void with no words would leave the record unable to say why the round ended. The **provider is told first**, and the `voided` transition is applied through the one status funnel afterwards: the send's order inverted, for the send's reason — a record that reads "voided" while the envelope is still collecting signatures is the failure that matters, and telling the provider first cannot produce it. An envelope that has already ended is refused, because an ending is part of the record; a provider that refuses the withdrawal is answered **409**, because it is telling us the round has ended on its side and the ending arrives on its own feed. One case is deliberately **not** a refusal: an envelope the provider says it **does not hold** — a connector re-pointed at another account — ends the record's own row anyway, because refusing it would leave the one-live-envelope rule blocking every later send over a round that does not exist. The entry is narrated `envelope.voided` at the standing record tier **with the voider as its actor**, which is the one ending that names a person; the same verb arriving from the provider's own console still carries no actor, and the feed's sentence selects on which. After a void — and after a decline — the contract **sends again**, because the partial unique index holds only while an envelope is `sent`. The row's action cell, the void dialog, and the extended webhook note are **DES-038**.
- **Addendum (2026-08-16, M15/5)** — The **executed copy comes back on its own**, which is the second half of the milestone's sentence. When the one status funnel applies `signed`, the caller asks the pipeline for an executed-copy fetch — one new domain method on the job queue (`requestExecutedCopyFetch`), never a generic enqueue — **after** the transition has committed, because that function owns its transaction and has no hook inside it. The worker then downloads the signed PDF through the adapter, appends it to the chain the send left from as a round of kind `executed`, sets the CTR-014 pin on it, and narrates both with **no actor**, so the feed reads it as the integration speaking. The append runs through the **one version write path** shared with the upload route, under the owning contract's row lock: same numbering, same 1..n chain, same derivations owed. The round is recorded against the person who **sent** the envelope, because the integration holds no account and the send is the nearest human act behind the file. **The status advance is conditional and never regresses**: from the `signature` stage the contract moves to the first live status by display order that maps to `active` (CTR-001), narrated as its own entry with no actor; from any other stage the paper still files, the pin is still set, the completion is still narrated, and the status is left alone — the integration never drags a draft forward and never pulls a finished record back. The move starts at `signature`, already past `approval`, so **it cannot cross CTR-012's soft gate** and there is nothing for an override to record. **Failure follows the M12 derived-artifact pattern**: `contract_envelopes.executed_fetch` runs `pending | ready | failed`, the provider's terminal errors are settled at once, transient ones retry until the queue's bound runs out, and either way the state on the row is the record — after which the manual hand-off is the answer, exactly as it is for an install with no connector. A job lost between the commit and the queue send is recovered by an **executed-copy boot sweep** beside M12/6's, which re-asks for every signed envelope still `pending` and walks past every `failed` one. The row draws the file it produced through its own `executed_version_id` rather than through the document's pin, because a chain can hold two rounds both called `executed` and a pin a team moved by hand must not change what an older row says it filed. The row's executed-file cell, the whole C20 note, and the send dialog's C12 note are **DES-039**.
- **Addendum (2026-08-16, M15/6)** — The **reconciliation sweep** closes the milestone's last promise: an install the internet cannot reach converges anyway (story 22). Connect needs a publicly reachable address and many self-hosted installs have none, so the worker asks the provider where every live envelope stands and applies what it is told. **Connect stays the primary feed and this is the fallback** — it is the same walk M12/6 uses (keyset paging, a refusal bound, a signal that stops it between rows), repeated on an interval rather than run once at boot, because it is waiting for somebody to sign and no single walk can see that. The two feeds **know nothing about each other and need no coordination**: they funnel into `applyEnvelopeStatus`, so a status the webhook already delivered writes nothing here — no second row, no second entry on the feed. A `signed` the sweep applies hangs its executed-copy fetch off the same `applied` result the webhook's does, so a swept envelope ends exactly as a delivered one: one path, one narration, one pinned copy. It also recovers the one delivery Connect will **never resend** — a delivery that arrives before the send transaction commits names an envelope this install does not hold, and the route acknowledges it rather than refusing, so nothing more is coming for that envelope and the sweep is what un-strands it. **The sweep is a reader and never a writer of its own opinion**: an envelope the provider will not speak about and a provider that cannot be reached both leave the record exactly as it was — nothing marked, nothing failed, nothing given up on — and the next round asks again. The provider saying "still out" is not a change and does not reach the funnel. The shape, the interval, and the outage rule are recorded against **TECH-007**.
- **Addendum (2026-08-16, M15/7)** — **A signer's name and email address are kept on the `envelope.sent` activity entry, and therefore also leave the process on stdout.** The entry carries them because the envelope's own signer rows go when the record does, and the entry is then the only thing left that says who was asked — the same reason the document verbs name the file they acted on. DD-017's SIEM clause emits every appended row through the application logger, and `lib/activity-emitter.ts` forbids redacting the emitted copy: `activity_log` is append-only, so a redacted line would hide nothing that the stored row does not already keep, and it would make the shipped copy and the record disagree — the one thing a SIEM copy must never do. A secret is kept out at the writer instead, which is why the connector's RSA key and Connect secret never reach a payload at all. **A signer is not a secret and not a user of this install**, which is what makes this different from the addresses `user.invited` already carries: an external signer never agreed to anything here and has no account to be erased with. The v1 posture is that the record wins — an audit entry that cannot say who was asked to sign is not an audit entry — and the obligation this leaves is named rather than solved: an erasure path for a person who is only ever a signer is filed as its own question, alongside DOC-010's lawful erasure for documents. Nothing here changes what the API answers or what the feed prints; the sentence on the record has never named the signers.
- **Addendum (2026-08-16, [#278](https://github.com/juggernog20/OpenLaw/issues/278))** — **The resolver caches the driver it built, keyed on the connector row's identity and its `updatedAt`.** The mailer-resolver pattern above says the row is read live so a rotated key applies to the next call with no restart, and the resolver took that to mean building a fresh `DocuSignProvider` every time. A driver caches the access token it minted and the account it discovered, on the instance, so a fresh one per resolution threw both away: the reconciliation sweep resolves once per page, and a five-minute round on a self-hosted install therefore minted a JWT every five minutes and discarded one that had not expired — against the endpoint DocuSign rate-limits hardest. **The read is what must stay live, not the build.** The row is still read on every resolution; only the construction is skipped when the key matches, and a save changes `updatedAt` (the column's own `$onUpdate`), so the very next call builds from the new credentials. The rotation promise is unchanged and asserted. **The cache has no lifetime of its own** — the driver refreshes its own token, so a ceiling would throw away a working driver to rebuild an identical one — and it holds at most one entry, because the table holds at most one row per adapter. An entry is dropped when the row goes, so a removed connector never leaves credentials behind in a process. The one thing it cannot see is two saves inside the same millisecond, which the route's own row lock makes serial and which costs one stale driver until the next save. **The mailer resolver deliberately does not follow.** It builds a nodemailer transport per resolution, and a transport holds no minted credential and repeats no grant — SMTP authenticates per connection, and the non-pooled transport opens one per send whether it was cached or not. There is nothing there to keep, so the two resolvers differ, for that reason and not by oversight.
- **Addendum (2026-08-16, [#273](https://github.com/juggernog20/OpenLaw/issues/273))** — **A configured connector can be turned off, and it can be taken out.** M15 shipped neither, so an install that configured one had one for good — and CTR-013's promise that a team which never configures a connector loses nothing was reachable only by never having configured one. Both land, because they are **two different acts and not two designs for one**. Turning it off (`disabled_at`, the `archived_at` shape every taxonomy table uses) keeps the row and both credentials, and the resolver answers `null` — so every surface answers exactly as it does on an install with no connector, the send control leaves the record by the DES-035 absence rule, and the manual hand-off is the path again. Taking it out deletes the row and the two secrets with it, for the team that wants the credentials gone rather than parked. **There is deliberately no third answer between "configured" and "not":** a `disabled` state that callers had to branch on would be a second rule to keep in step at every seam, for a distinction only the settings pane is interested in. **A live envelope refuses the delete and not the switch.** Deleting strands a round that is still out for good — nothing left to void it with, and nothing for the reconciliation sweep to ask — so the refusal names how many are out and points at the switch; turning the connector off strands nothing, because turning it back on picks the round up where the sweep left it, and an Administrator who has to stop the sending **now** must never be blocked by paper somebody else has out. Three verbs join the DD-017 vocabulary — `signing_connector.disabled`, `.enabled`, `.removed`, all `admin_only` — rather than one generic edit: "was the key still here last Tuesday" is the question a credential's history exists to answer. The disable entry carries how many rounds were out at that moment, because they stand still while the connector is off and nothing else afterwards says so; the removal entry carries the estate and the integration key, because after the row is gone it is the only thing left that says which account this install was talking to. Neither carries a secret, for the reason the whole namespace does not: `activity_log` is append-only. The pane draws the switch inline and the removal behind a confirmation that names the switch, because most people who reach for "remove" want the reversible thing. Settings placement is SET-007's, unchanged. **The M15 demo stops skipping itself**: the zero-config half now removes the connector an earlier run left behind, so the promise is proved on the never-reset instance and not only on CI's fresh volumes.
- **Addendum (2026-08-16, [#280](https://github.com/juggernog20/OpenLaw/issues/280))** — **A person who is only ever a signer gets an erasure path, and it rewrites the entry in place.** The addendum above recorded the posture and named this as the open question. It is answered: an Administrator-only `POST /api/v1/signer-erasures` takes an address, rewrites the name and the address to `[erased]` in every `envelope.sent` payload holding it, and deletes the `contract_envelope_signers` rows for it. **The shape stays.** The signer array keeps its length and its order, so the entry still says how many people were asked and in what position — the part of the record that is about the contract rather than about the person. That is what makes the surviving entry still an audit record: an entry that lost its signers would stop being one, and an entry that keeps a tombstone in each slot says plainly that somebody exercised a right. **This is the one `UPDATE` on `activity_log`, and it is a named exception rather than a crack in the rule.** DD-017 forbids mutation because corrections are appended; this is not a correction — no fact recorded here was wrong — and there is no way to honour a lawful-erasure request by appending. The exception is confined to one module, one action slug, and two keys inside it. The erasure is then itself **appended**, `admin_only`, hanging off `system`, carrying counts and **no address**: an entry naming the person who asked to be forgotten would put the address straight back into the table it was just taken out of. **A user of this install is refused.** Their address sits in payloads that are about them as a colleague, and those have a different answer (DD-013's archival); a half-answer nobody could reason about afterwards is worse than a refusal that names the right route. An address that was never a signer's answers 200 with zeros — the request is satisfied either way, and refusing would make the seam a way to ask whether an address is in the record. **The copies already shipped are the operator's.** DD-017's SIEM clause emits every appended row through the application logger, so a signer's address has left the process long before a request arrives, under whatever retention the deployer's shipper runs; nothing here can recall it and nothing here pretends to. That is stated in `docs/DEPLOYMENT.md`, where the person who owns those copies will read it, and not only here. `contract_envelope_signers` and the activity payload therefore **do not diverge**: the rows are ordinary data and are deleted, the payload is append-only and is redacted, and one route does both in one transaction.
- **Addendum (2026-08-21, [#391](https://github.com/juggernog20/OpenLaw/issues/391)) — one address, one signer on one envelope.** `contract_envelope_signers` was unique on `(envelope_id, signing_order)` and on nothing else, so the **position** was protected and the **person** was not: the same address could sit on one envelope twice. It now carries a second unique index, on `(envelope_id, lower(email))`. Case-insensitive, because that is how the send compares addresses, how the erasure path matches them, and how `users_email_unique` reads one; the column itself stays verbatim, because what the record has to show a week later is what the sender typed.

  **This is a backstop, not a new rule.** The send route has refused a repeated address since the day it shipped — "Each signer needs their own email address", 422 — and it is the table's only writer; the signer-erasure path deletes rows and never adds one. So the index changes nothing an API client can see, and no install should hold a row that violates it. It is worth having because the address is a signer's whole identity here: the erasure path finds a signer by it and by nothing else, and two rows nothing can tell apart are two rows an erasure cannot reason about.

  **The migration refuses rather than resolves, and that is the opposite of 0065's answer two decisions above.** A duplicate approver-group name has an obvious human fix, so `0065` applies it. A duplicate signer row does not: an envelope's signer list is the record of who was asked, and dropping one of two rows would make the record say the sender asked one person when they asked two. `0066` therefore names the envelope and the address and stops the upgrade, on 0060's pattern — a guard for a state no install can reach, kept because the raw index build would otherwise fail with nothing said about which rows collided.

- **Addendum (2026-08-16, [#259](https://github.com/juggernog20/OpenLaw/issues/259))** — **The connector's two secrets are encrypted at rest.** The M15/1 addendum above recorded them as stored plaintext, the accepted v1 posture, and named this table as the second entry on a future pass. That pass happened (**TECH-022**): `private_key` and `webhook_secret` are declared with `encryptedText`, so they are sealed on the way to Postgres and opened on the way back with a key held outside the database. The exposure this closes is **impersonation, not disclosure** — whoever holds the RSA key mints JWT assertions as the install's integration user, and whoever holds the Connect secret forges a delivery saying a contract was signed when it was not. A `pg_dump` is a routine artefact and a much lower bar than a live database. **Nothing above changes.** The credentials are still org data read live per use, the resolver still reads the row on every resolution, and a rotation still applies to the next call with no restart — the seal sits below all of that, in the schema, where no caller can forget it. Two seams did move, both small and both for the same reason: an unopenable value reads as an unset credential rather than throwing, so the pane an Administrator recovers in still draws; and a save that keeps the stored secrets now leaves those columns **out** of the `UPDATE` instead of writing them back, so saving the estate while the key is wrong cannot overwrite a credential the install could still recover.

## CTR-014 — Documents: primary version chain, executed pin, generate-redline capability

- **Status** — Accepted
- **Date** — 2026-08-02
- **Context** — How drafts → redlines → executed relate to the Contract record (gates F.3; the deep file mechanics belong to the Documents grill). Blair accepted the version-chain recommendation and added: "we'll also want the functionality to run a redline against the previous version."
- **Decision** —
  - Each contract designates one **primary document** with an ordered **version chain**; every version is tagged with kind — `draft_ours | redline_theirs | redline_ours | executed | amendment` — plus an optional note.
  - The **executed version is pinned**: it's what previews, exports, and AI analysis (CTR-008) target by default.
  - Loose attachments (schedules, certificates) attach to the contract outside the chain.
  - **Generate-redline capability** (user addition): from any version, the system can produce a comparison against the previous version (Word-compare-style redline artifact, saved into the chain as a generated file). Comparison engine mechanics (OOXML diff vs external tool) → Documents/tech-stack grills, where the existing K.H4 redline-strategy row already lives.
  - **Key clauses (F.3) are not a clause model** — they render AI-extracted fields per CTR-008 (governing law, indemnity cap, etc. as fields with prompts).
- **Rationale** — The ordered chain kills filename archaeology; the executed pin gives every downstream feature one authoritative file; field extraction covers the read-side of clauses without an Ironclad-scale clause library.
- **Alternatives considered** — Loose docs + executed flag: negotiation history as filenames. Clause-level model: heavy parse/storage build v1 doesn't need.
- **Consequences** — `documents` schema (Documents grill) must support: contract primary-document designation, version ordering, version kind, generated-artifact provenance. _Settled in M11/4: the primary-document designation is **`contracts.primary_document_id`**, an FK on the contract rather than a flag on each document — one column is the exactly-one rule stated as a shape, where a flag needs a partial unique index to say the same thing. The first document uploaded takes it; there is no clear, so it moves or it stays._ Grill-plan F.3 unblocked (renders CTR-008 fields); K.H3/K.H4 stay DOC-gated but now have the contract-side contract to satisfy.
- **Addendum (2026-08-16, M15/5)** — The executed pin is **set automatically for the first time**. It has existed since M11/4 with by-hand set and clear routes; M15/5 is the slice that makes the e-signature return set it, which is what this decision promised the pin would be for. Two rules are stated here because the integration is the first writer that could break them. **The pin is set explicitly, never inferred from a version's kind** — the round the integration files is tagged `executed` _and_ pinned by a separate write, exactly as a by-hand pin is, because a chain can hold two rounds both called `executed` and only one of them is the record's signed copy. **The pin stays the document's, not the envelope's**: a team that moves it afterwards is not corrected by the integration, and the envelope keeps its own `executed_version_id` so an older row still draws the file it filed. Both are consequences of the pin being a decision about the record rather than a property of a file.
- **Addendum (2026-08-18)** — **The by-hand pin toggle moved off the row and into the version's overflow menu**, as "Mark as executed copy" / "Unmark as executed copy". The inline icon-only button tested badly: nothing on the row said what a lone pin glyph did, and the label wasn't visible without a tooltip. The two designations still don't share a menu item — the document's Primary designation ("Make primary") and the version's Executed pin are worded and act apart, so the "two facts, one word" collision this decision's UI already avoided in the Executed pill and the Executed badge isn't reintroduced in the menu. The current version's pin item lives in the document's own overflow menu, beside Make primary; a superseded round has no document-level act to sit next to, so it gets a one-item menu of its own on its own row — the control is still on the version's own row, per this decision's original placement rule, only inside a menu now rather than inline.
- **Addendum (2026-08-19, #326)** — **A sixth kind, `draft_theirs`, for the counterparty's own first draft.** This decision's original five had no slot for the round that opens a negotiation on their paper, so it had to be mislabelled: `redline_theirs` claims a markup of a round that does not exist yet, and `draft_ours` names the wrong author. Neither is a small inaccuracy on a chain whose whole job is to be the negotiation's history. **The list now reads in two axes rather than one.** The two `draft_*` kinds are **originating** rounds — paper somebody wrote — and the two `redline_*` kinds are **markups** of a round already on the chain; the second axis is whose paper it is. That is why both sides need a draft and why the sixth kind was a gap rather than a convenience. It is shaped exactly like `draft_ours`: an ordinary uploaded kind, with `source` still `uploaded`, no comparison operands, and no bearing on the executed pin, which stays explicit and set by hand or by the integration per the M15/5 addendum above. **The pill colour says whose paper it is; the label says what the round is.** `draft_theirs` therefore takes the same amber as `redline_theirs` rather than a sixth colour family, exactly as `draft_ours` and `redline_ours` already share the informational pair. A colour of its own would make one column encode two facts at once, and the palette holds no spare family that would not misread — `assigned` sits within a shade of DES-009's confidentiality marker on the light theme, `neutral` is the amendment's, and the two red families would call a routine round a problem. **The kind set stays fixed, not admin-configurable**, for the reason this decision already gives: code branches on it. Widening the check constraint is safe in place — every existing row still satisfies the wider rule — so migration `0055_document_version_draft_theirs` drops and re-adds `document_versions_kind_check` with no data change and no backfill.
- **Addendum (2026-08-22, M21A, [#438](https://github.com/juggernog20/OpenLaw/issues/438))** — **The kind is correctable, and only the kind.** This decision fixes a version's kind at the moment the round is written, and until now nothing could change one: there is no `UPDATE` against `document_versions` anywhere in the API. Nobody had to defend that while every round arrived from the person who knew what it was. CMT-011 puts a second act between a file and the chain — a lawyer files paper that came in on a thread — and a kind chosen in a second, over a file somebody else sent, is a judgement that will sometimes be wrong. A chain whose whole job is to be the negotiation's history cannot be a history that stays wrong. **A Member+ may change a version's kind and nothing else about the version moves**: not the bytes, not the order, not the note, not the author, not the round's place in the chain. The round is a fact and the kind is a judgement about it, which is the line this draws and the reason only one side of it is writable. **It narrates** (DD-017) — `document.version_kind_changed`, carrying the kind before and the kind after — so a correction is on the record rather than quietly applied. **The executed pin is untouched in both directions**: the pin is set explicitly and never inferred from a kind (the M15/5 addendum above), so naming a round `executed` does not pin it and naming it something else does not clear the pin. **`generated_redline` is outside the correctable set** when M32 brings it, and no hand-set kind may be changed into it: that name says how a file was made, which is a fact about its provenance rather than a judgement about the round.

## CTR-015 — Relations: parent_id hierarchy + typed directional links, no inheritance

- **Status** — Accepted
- **Date** — 2026-08-02
- **Context** — Contract relationships (MSA→SOW trees, amendments, renewal successors). Pulled forward by CTR-007, whose renewal routing requires links that _identify_ a renewal. MTR-015 settled the matters sibling with untyped links.
- **Decision** —
  - **Hierarchy**: `contracts.parent_id` — single parent, arbitrary depth, no cycles (application-enforced). MSA → SOWs; substantial amendments as child contracts.
  - **Typed directional links**: `contract_relations(from_contract_id, to_contract_id, relation_type)` with `relation_type` = `related` (symmetric) | `renews` | `amends` (directional). Renewal reporting reads `renews` links (plus confirmed rolls from the activity log) per CTR-007. Minor amendments may instead live as doc-chain versions per CTR-014 — team's choice per case.
  - **No cascade/inheritance semantics** (MTR-015 stance): status, team, confidentiality never flow between related contracts. Inaccessible relatives render as "restricted contract".
- **Rationale** — The type upgrade over MTR-015 is forced by CTR-007: "a renewal is identified by the link, not by record shape". parent_id keeps the most common structure (MSA trees) cheap to query and render.
- **Alternatives considered** — Untyped MTR-015 copy: renewal reporting has no datum. Links-only (no parent FK): MSA trees become graph traversal.
- **Implementation note (2026-08-17, M16/5) — the write side landed here; the surfaces are M17's.** This decision is deliberately split across two milestones, and the split is otherwise invisible to a later reader of the plan. **M16 landed the rows and the rules**: `contracts.parent_id`, `contract_relations` with the `related | renews | amends` union, and both CTR-015 guards, in migration `0048_contract_relations`. **M17 lands every read and management surface**: the relations panel, the hierarchy breadcrumb, manual link creation and removal, and the "restricted contract" rendering of a relative the viewer cannot reach. M16 draws no relations UI at all beyond the routing act itself. The reason for the split is CTR-007: renewal routing is the feature that first _writes_ a link, and a schema that arrives with the feature that needs it is the incremental-schema rule (TECH-014) doing its job.
  - **Both guards are stated twice, on purpose.** The compound primary key refuses a second row for one pair and one type; the `parent_id <> id` and `from <> to` checks refuse the degenerate self-cases. Those are what the row obeys whichever code wrote it. What a constraint cannot do is _answer_, so one shared write path (`lib/contract-relations.ts`) asks both questions first and refuses by name — `urn:openlaw:problem:contract-relation-exists` and `urn:openlaw:problem:contract-parent-cycle` — and M17's manual linking calls the same two functions rather than re-stating the rules. The write path also serializes both writes under one transaction-scoped advisory lock, because neither guard is a single row's to hold in a race: a cycle can be threaded by two concurrent parent writes that each walk a chain the other has not committed, and a symmetric `related` mirror is two different keys the compound key cannot see as one.
  - **A cycle is a walk and cannot be anything else.** One row can say a contract is not its own parent; it cannot say the proposed parent is not already three levels beneath it. So the parent write walks up from the proposed parent and refuses the moment it meets the child. The walk carries an explicit depth ceiling as well, because a bound that depends on the invariant it is defending is not a bound.
  - **`related` is symmetric, so its duplicate check looks both ways.** For an unordered pair the primary key alone would let the mirror row in, and two rows saying one symmetric thing is exactly the duplicate this decision forbids. The two directional types are checked one way, because for them the direction _is_ the statement: A renewing B and B renewing A are two different claims.
  - **None of these refusals is reachable from M16's own routing**, and that is recorded rather than hidden: every routed create makes a _new_ record, which has no descendants to loop through, no links to duplicate, and no `related` link at all. The row rules are proved at the row in the API suite; the application refusals are proved through the seam by M17's manual linking, which is the first caller that can reach them. This milestone deliberately does not reach past its own seams to prove them sooner.
  - **Each write is narrated as its own closed-union verb** — `contract.parent_set` and `contract.relation_added` — at the standing record tier, hung on the record that changed. Nothing is written on the far end: no-cascade is not only about status and confidentiality, and a feed entry on a record whose row nobody touched would be the log asserting an edit that never happened.
- **Implementation note (2026-08-17, M17)** — **The read and management surfaces landed, closing the M16/M17 split.** M16/5 wrote the rows and the rules; M17 landed every surface that reads them. The relations panel, the hierarchy breadcrumb (the parent chain rendered root-first above the record heading), manual link creation and removal through the link dialog, manual parent set and remove, and the "restricted contract" placeholder for a relative the viewer cannot reach — all shipped and proved through the seam. CTR-018's link-time confidentiality nudge shipped with the link dialog. The application refusals — cycle, duplicate, and self-link — are all reachable from the manual linking paths and proved through them. CTR-019's end-of-life signal landed in the same milestone: `ended_at` stamped on entry into the `ended` stage, cleared on reopen, the record staying fully writable throughout.
- **Consequences** — `parent_id` column + `contract_relations` table in SCHEMA.md. Duplicate-direction guard (one row per pair per type) application-enforced. Contract details needs hierarchy breadcrumb + relations panel (screen batches).

## CTR-020 — The taxonomy archive guards: types reassign, statuses block

- **Status** — Accepted
- **Date** — 2026-08-13
- **Context** — M8 arms the SET-003 guards on both contract taxonomies (#113). SET-003 fixes the shape in one sentence — an in-use value "shows the live-usage count and requires a reassignment target", while "surfaces with structural minimums (statuses: ≥1 per stage per CTR-001) block instead" — but it does not say what a status does when contracts hold it and the floor is satisfied. ENT-009 answered the counting question for the type side and left the status side open.
- **Decision** —
  - **Contract types reassign.** Archiving a type contracts still hold refuses without a `reassignToId`, reporting the live count; with one, every contract on the type moves to the target and the type archives, in one transaction. Hard delete of an in-use type refuses with the same count.
  - **Contract statuses block.** Archiving a status contracts still hold refuses with the live count and offers nothing else — no reassignment target, no select in the dialog. The Administrator moves the contracts, then archives the status. Hard delete refuses the same way. This is on top of the CTR-001 floor, which is checked first.
  - **Both count archived contracts**, per ENT-009's rule inherited by this taxonomy: the counted set, the moved set, and the set the FK protects are one set.
  - **A guard-driven type reassignment is a system move, not a re-type.** It does not run MTR-014's hard-required check (`assertRequiredCustomFields` is the one entry point, and this path does not call it), and it retains every `custom_fields` value. Each moved contract gets its own activity entry under `contract.type_reassigned`, not `contract.updated`.
- **Rationale** — Type is a policy carrier (CTR-002); one type is a defensible substitute for another, so a bulk move is a decision an Administrator can make once. Status is a position in a lifecycle (CTR-001): which status each contract belongs on is a per-record judgement, and a bulk move would silently rewrite the pipeline. Refusing the reassignment on the type side instead would be worse than either — it would strand records on an archived type, which is the exact failure the guard exists to prevent.
- **Alternatives considered** — Reassignment for statuses too (bulk-rewrites lifecycle positions nobody reviewed); refusing the type archive outright and making the Administrator re-type every contract (the guard's whole point is that it does not); skipping archived contracts in the count (splits the counted set from the FK set, and a restore would resurrect a reference to an archived value).
- **Consequences** — Clearing a status held by an archived contract takes a restore, a move, and an archive again, because an archived contract refuses edits. That cost is accepted: one counting rule everywhere beats a second rule for archived rows. The type guard's bulk move can leave a moved contract missing a field the new type marks required — a real gap, filled on the record, never papered over.

## CTR-021 — Contributor contract access: the team row is the grant, read-only in M9

- **Status** — Accepted
- **Date** — 2026-08-13
- **Context** — M9 gives a Contributor their first record-level access (#127), so the DD-016 tier filter has a real second audience. DD-015 says a Contributor is "made, not born" and sees "only matters/contracts they are explicitly added to", but it does not say which row in the schema counts as "added", nor what happens on a contract they are not on. It also grants them a business/legal editable-field split that the M9 record does not yet carry.
- **Decision** —
  - **Any `contract_team` row is the grant.** A Contributor reads a contract when they hold a row on it, whatever role that row carries — `member`, `watcher`, `contributor`, or `creator`. The act of adding someone to the team is what grants the access, so no second rule decides which roles count.
  - **One predicate, both readers.** The list filters on it and the record read applies it beside the number. A contract a Contributor holds no row on answers **404 with the same body as a contract that does not exist** — never 403, never a locked page. Access is not advertised.
  - **An empty scope is an empty list**, not a refusal. A Contributor on no contract gets the list's own empty state.
  - **Read-only in M9.** Every mutation seam stays Member+: create, the per-field PATCH, status, archive, restore, team, counterparties, value, and custom fields. So does the picker read behind the create dialog and the record's selects — the pickers exist to commit from.
  - **The DD-015 business/legal field split is not built here.** It lands with the field grid.
  - **Business Users stay refused** on every contract surface until intake links a requester to a record (M19–M21).
- **Rationale** — Keying on the row rather than on the row's role keeps one act (add to the team) as the whole grant, which is what an Administrator can reason about. Answering 404 rather than 403 is the DD-014/DD-016 silent-omission rule applied to the record itself: a refusal that names the record tells a Contributor a contract exists, and existence is sometimes the sensitive part. One predicate over both readers is what stops a contract appearing in a list that the record read then refuses.
- **Alternatives considered** — Granting only on a `contributor`-role row (leaves a Contributor added as a watcher with a row nobody honours); 403 on a contract they are not on (leaks the record's existence); giving a Contributor the picker reads so the record's selects render from a live list (they commit nothing, and the record read already carries every name the page draws); building the DD-015 field split now (the grid is a milestone of its own, and a half-built split would be a permission rule nobody reviewed).
- **Consequences** — Removing a Contributor's last team row takes their read away immediately, because the guard reads the rows live on every request. The Contracts destination appears in a Contributor's nav. The record page renders the DES-017 inline surface with its inputs inert — the same treatment an archived contract already gets — with archive and restore absent rather than disabled, since a Contributor never gets them. The M9 comment and activity surfaces mount on this same scope.

## CTR-022 — The Confidential flag on a contract: the Owner joins, and the mention rule replaces the watcher grant

- **Status** — Accepted
- **Date** — 2026-08-14
- **Context** — M10 builds DD-014's Confidential flag on the contract record (#146). DD-014 was written about matters and says two things this module has to answer for contracts. First, it names the actor set as "Administrators and the matter creator" — but a contract has a single accountable person, its Owner (`manager_id`, CTR-004), and DD-014's team model has no equivalent. Second, DES-009's Tier 3 affordance offers to add a mentioned outsider to the confidential record as a watcher, which CMT-007 has since rejected for every record: the typeahead offers only people the record can reach, and a mention grants nothing.
- **Decision** —
  - **The Owner joins the actor set.** An Administrator, the contract's creator (its `creator` team row), or its Owner may set the flag and clear it. Nobody else may, and being on the team is not enough.
  - **The Owner joins the access set.** A confidential contract is reached by its named team, its Owner, and Administrators. The Owner clause holds with no team row, so a contract can never vanish from the person accountable for it. This is the same extension read from the other side, and it is already in the shared access module (CTR-021).
  - **The flag is settable at creation.** The person creating the record is its creator, so the actor check is satisfied by definition, and a record that must be walled off is never visible to the wrong audience even briefly.
  - **Two refusals, and the difference is deliberate.** A viewer who reaches the record but is none of the three actors is refused **403** — they can already see the record, so nothing is hidden by pretending otherwise. A viewer who does not reach the record at all is answered the **CTR-021 404**, with the same body as a contract that does not exist. Reach is decided by the shared module, so the write cannot answer a question the read would have refused to admit was there.
  - **The flag is an edit.** An archived contract refuses it like every other edit (CTR-019's archive rule, unchanged).
  - **CMT-007 supersedes DES-009's Tier-3 watcher grant, for contracts.** The composer offers nobody the record cannot reach and confirms no membership. DES-009's Tier 3 survives as the composer's confidential notice; its "they will be added as a watcher if you confirm" clause does not.
  - **Each set and each clear is its own activity action** — `contract.confidentiality_set` and `contract.confidentiality_cleared`, at the record-action tier (`working_team`, DD-017). One write serves both DD-017 surfaces: the record feed narrates it, and the Administrator-only audit log records it with actor and timestamp. The audit-log module needs no change.
- **Rationale** — The Owner is the one person a contract is accountable to; an Owner who cannot decide their own record's audience has to ask an Administrator for something they already carry the responsibility for, and an Owner who cannot see their own confidential record is a data-loss bug wearing a permission rule. Splitting 403 from 404 keeps DD-014's silence where silence is the point — existence is the sensitive part only for people who cannot see the record — and stops a genuine permission boundary reading to its own team as a missing record. Keeping the flag out of `contract.updated` is what makes DD-014's audit requirement a filter rather than a hunt through edit payloads.
- **Alternatives considered** — DD-014's actor set unchanged (leaves the accountable person asking an Administrator to protect their own contract, and leaves DD-014's matter-shaped team model governing a module that has an Owner column instead); 404 for every refused flag write (hides a real permission boundary from a viewer who is looking straight at the record, and reads as a bug); the whole team as actors (being able to work on a record is not a claim on who else may see it); keeping DES-009's add-as-watcher confirmation (it would grant access from the comment composer, which CMT-007 rejected for every record, and it is unbuildable against a typeahead that already excludes the person it would offer to add); folding the flag into `contract.updated`'s changed map (DD-014 wants the walling-off itself accountable, and a key inside an edit is not a slug an Administrator can filter on).
- **Consequences** — The flag joins the contract row and detail schemas and the create and patch payloads, so the OpenAPI document and the generated client carry it; the list keeps its no-count shape, because there is no total to scrub. Two slugs join the closed `ActivityAction` union and the narration layer. The three-actor rule has one home, beside the reach rule in the shared access module, because it is built out of reach — DES-009's "Manage team →" link and the record's flag control (#148) read the same answer rather than a second copy of it. DD-014's own text stays as written: this record is where the Contract module's extension lives, and the M22 DD-014 addendum records the Matter answer.

## CTR-023 — The team of a Confidential contract: the roster is an audience decision (extends CTR-022)

- **Status** — Accepted
- **Date** — 2026-08-14
- **Context** — CTR-004 makes the contract team a generous thing: any Legal Team Member or Administrator puts somebody on a contract or takes them off, because on an open record nothing about the roster is withheld from anybody. CTR-021 then made the team row the grant for a Contributor, and CTR-022 made it the grant for a confidential record. Once that happened, the roster stopped being only a working group. On a walled record, adding a person is the act of letting them in — it clears the flag for one person — and the generous rule let any Member do by roster edit what CTR-022 forbids them by switch. The affordances already disagreed with the capability: the DES-028 banner hides "Manage team →" from a plain Member, and the Team card 200px below it let them manage it anyway.
- **Decision** —
  - **On a Confidential contract, only CTR-022's three actors may change the team.** An Administrator, the contract's creator, or its Owner. Being on the team is not enough — the same sentence CTR-022 already wrote about the flag, now true of the two acts that have the same effect.
  - **It covers both directions.** `POST /contracts/:number/team` and `DELETE /contracts/:number/team/:userId/:role`. Taking somebody off a walled record is the same decision read the other way.
  - **An open contract is untouched.** CTR-004's rule stands wherever the flag is not set, which is most of the estate. The gate arrives with the flag and goes away with it, on the very same record.
  - **403, not 404.** They reach the record. This is CTR-022's own split, unchanged: existence is the sensitive part only for somebody who cannot see it.
  - **It is asked before the archived refusal**, so a viewer who may not decide the audience does not learn from a 409 that the write was otherwise theirs to make. The flag's own write already runs in that order.
  - **One rule, one place.** Both guards ask `confidentialityWrite`, the same function the flag control asks. The refusal sentence differs, because two acts decide the audience and each has to say which one was refused; the rule behind them is not copied.
  - **The web control goes inert, not absent.** The Team card's add control and each row's remove control are drawn and disabled for a viewer outside the three. Who is on the contract is a fact and stays readable; only the deciding is withheld. This is DES-028's treatment of the flag control, for DES-028's reason.
- **Rationale** — It makes one sentence true everywhere: you decide the audience, or you do not. The state before this was worse than either answer, because the banner's gate implied an intent the card's capability contradicted — and a reader who noticed would reasonably conclude the gate was the mistake. The cost lands where it should: a Member who needs a colleague on a confidential contract asks one of three people, on the thin slice of records that carry the flag.
- **Amends** — #147's acceptance criterion "team-row holders, the Owner, and Administrators mutate unchanged" no longer holds for the roster of a confidential contract. A team add by a plain Member on a walled record is a refused write from this decision onward. The M10/3 test that asserted it is amended in the same change, and the roster moved into a test of its own where the split can be stated rather than hidden behind one expected status. Everything else in that criterion — the title, the status, the counterparties, the archive and the restore — stands exactly as accepted.
- **Alternatives considered** — Leaving it (keeps a gate with a door beside it, and leaves CTR-022's "being on the team is not enough" false in practice); restricting the roster on every contract (CTR-004's generosity is right for an open record, and nothing in M10 argued against it — the flag is what changes the meaning of the act); hiding the controls instead of disabling them (the roster is a statement of fact, and a card that silently loses its controls reads as a bug rather than as a rule); allowing the add but not the remove (both change who is inside the wall, and a rule that holds in one direction only is a rule nobody can state).
- **Consequences** — Two route guards in the contracts module, both on the shared access module's answer. The Team card takes one new prop, read from the same client-side twin of `confidentialityWrite` that the flag control and the banner's link already use — so the three affordances cannot disagree with each other. No schema change, no new activity action: the roster's own two actions already record who changed the team. M22 gave the Matter team the corresponding DD-014 answer.

## CTR-024 — Bounding the lists: a keyset cursor, a server-fixed page, and no total

- **Status** — Accepted
- **Date** — 2026-08-14
- **Context** — `GET /contracts` answered every contract the viewer could reach, in one response, forever. So did one record's comment thread and one record's documents. None of the three has a ceiling: the contract list grows with use, a thread grows for as long as the record lives, and a contract holds as many documents as it needs (CTR-014). The house already answers this question twice — the activity feed and the audit log are both paged in the same shape — and `GET /contracts` already ordered by `contracts.number` descending with a comment saying no second sort key can tie. The keyset was sitting there unused.
- **Decision** —
  - **The shape is the one already shipped**, taken verbatim from the audit log: a **server-fixed page size**, a **keyset cursor that is the previous page's last row id**, the cursor row's own position **looked up from the table** so no client can page from a boundary that was never written, `PAGE_SIZE + 1` fetched and sliced to derive the cursor, and `nextCursor: string | null` in the envelope.
  - **Page size 50** on all three, matching the audit log — the other table. 25 is the feed's number, and a feed is read where a table is scanned.
  - **No total.** Numbered pages would need one; a scoped count is safe to compute but adds a query to every call and a second number to keep honest under DD-014. The client counts the rows it was given, which is the only number that cannot leak.
  - **The scope filters before the limit, never after.** `teamScope` for contracts, the DD-016 tier filter for comments, and DD-014's per-document audience for documents all sit in the `WHERE` clause, so a page is 50 rows the viewer can already reach. An implementation that limited first and filtered after would answer pages that shrink by however many hidden rows sat in the window, and a page length that varies with what is hidden is an existence leak. **This gets a named test on each of the three, not a comment.**
  - **The cursor is resolved under the viewer's own scope.** A cursor naming a contract they cannot reach, or a comment in a tier they are not in the room for, resolves to NULL and answers an empty page. A boundary that resolved outside the scope would turn the cursor into an oracle for records the viewer is not allowed to know exist.
  - **The three orders, and the direction each pages in.** Contracts page **down** by `number` descending — monotonic and unique, so no tie-break. Documents page **down** by `(created_at, id)` descending, and a document's version chain rides with it whole: a negotiation history split across two pages is not a history. Comments page **backwards**: a read answers the **newest** 50, ordered oldest-first inside the page — CMT-002 is unchanged for what a reader sees — and `nextCursor` walks into the older thread. A panel that opened on the oldest fifty of a two-year conversation would be paging away from what the reader came for.
  - **A write that answers the whole list answers the first page of it.** The two document writes that change more than one row — the primary designation and the hard delete — return the first page and its cursor. A section that had paged further down starts again from the top: the list it is given is the list it draws.
  - **Bounded now, and only these three.** Entities, users, and the taxonomies are left alone: the first two run to tens or low hundreds and are pickers as much as lists, and taxonomy is bounded by hand. Adding a cursor to a list that cannot grow adds a paging foot to a surface that will never show it.
- **Rationale** — One unbounded read is enough to make an instance unusable, and it fails worst on the deployment with the most data. Reusing the audit log's shape verbatim means there is one paging idiom in the codebase rather than three, and the properties that took thought there — the cursor looked up rather than trusted, the extra row instead of a count — are inherited rather than re-derived. Refusing a total is what keeps the bound compatible with DD-014: a number is a leak like any other, and the contract list already earned its no-count shape when the flag landed (CTR-022).
- **Alternatives considered** — Offset paging (rows shift under a reader as records are created, so a boundary duplicates or skips, and a deep offset scans everything before it anyway); a client-supplied page size (turns one request back into the whole-table scan this closes); a total beside the cursor (a second number to keep honest under DD-014, for a foot that does not need it); a timestamp cursor on the contract list (it has a monotonic unique key already, and a timestamp would need the tie-break the id was going to be); bounding entities and users too (see the last decision point); leaving comments and documents for a later ticket (they are the two lists that grow per record, so a bound the record surfaces do not have is the bound that will be missing when it matters).
- **Consequences** — Three routes take a `cursor` query parameter and answer a `nextCursor`, so the OpenAPI document and the generated client carry it. `DocumentsEnvelope` gains the cursor, which puts it on the two document writes that answer the whole list. The contracts list's sub-bar can no longer state a total, so it says what is on screen whenever that is not the whole list. **Sorting and filtering the contract list inherit this decision and have to extend it:** a keyset on `number` is the whole answer only while `number` is the only order, and a sortable column needs its own cursor pair with a unique tie-break. Both stay out of scope here. DES-031 is the surface half of this decision.

- **Addendum (2026-08-21, [#390](https://github.com/juggernog20/OpenLaw/issues/390)) — the rule for whether a new list pages at all.** The decision above bounds three named routes and says "only these three". Two more were already paged before it was written — the per-record activity feed and the audit log, the pair its own context calls "the house already answers this question twice" and whose shape it copied — and two have joined since: the notification bell, one factory registered twice for the two shells. Seven paged routes, six source sites, one idiom. The API and domain core review found the same test applied consistently across all of them and asked for it in writing; M22 then applied it to the Matters reader without re-deriving it.

  **The test is cardinality, and nothing else. A list route pages if and only if the number of rows it can answer is unbounded in normal use.** Bounded means bounded by something real — a write-time cap, an admin-only writer, a fixed `LIMIT`, or a set the build itself enumerates.

  What that rules out is the tempting shorthand, and the review's own draft of this rule got it wrong: **"it is a per-record child list" is not an exemption.** Three of the seven paged routes are exactly that — a record's comments, a record's activity, a record's documents. A thread grows for as long as the record lives, and per-record scoping does not bound it, it only makes the unbounded thing smaller to start with. Per-record and admin-seeded are _usual reasons_ a list turns out bounded, never a licence to skip the question.

  **A bound is hard or it is a judgement, and the two are not the same claim.** Three of the four are hard, in the sense that no sequence of user actions can exceed them: a write-time cap (`MAX_LIST_VIEWS_PER_SURFACE` on saved views), a fixed `LIMIT` (the counterparty and link-candidate searches — the second also refuses to answer without a query; the first deliberately answers an empty one with the first names alphabetically, and the `LIMIT` is the bound either way), and a set the build itself enumerates. A fourth is administrative: the four taxonomies, their type-field lists, the statuses, the custom-field catalogue, the approver groups, the intake links, and the auth settings grow only when an Administrator writes them, which is a bound on intent rather than on arithmetic — strong enough to rely on, and worth naming as the weaker kind. **The user roster is not in that list, because its writer is not only the Administrator:** staff rows arrive by invite or setup, but a Business User row is JIT-created the moment anyone on an allowed email domain redeems a magic link or completes an SSO sign-in (the databaseHook in `apps/api/src/auth/instance.ts`). The Administrator owns the domain allowlist, not each row, so the unpaged users list rests on the org's own headcount behind that policy — a fact about the org, kin to the entities registry's bound below, and the honest name for it.

  **The per-record lists are the judgement, and they are named as one.** A contract's tasks, key dates, approvals, envelopes, and relations answer whole because nobody puts a thousand key dates on one contract — not because anything stops them. That is CTR-024's own call above ("adding a cursor to a list that cannot grow adds a paging foot to a surface that will never show it") and this addendum does not reopen it. It does mark them as the set to revisit first if an install ever shows one running long, and it warns the next module against reading "per-record" as an answer: the three lists that **do** page are per-record too. The portal's own Request list is per-person and argued in place, on the same footing.

  **A new list that fits none of those bounds pages, and it pages in this decision's shape** — page size from the two already in use, cursor looked up under the viewer's scope, `PAGE_SIZE + 1` sliced, no total.

  **One route is unargued and is left as it stands: `GET /entities`.** It answers the whole registry with no cursor, no cap, and a `requireMember` writer, so it is the one unpaged list whose bound is a fact about legal entities rather than a fact about the code. A registry of the entities an org actually has is dozens of rows (ENT-001), so this is not a defect and is not being fixed here. It is named so the next reader finds it named rather than finding it.

- **Addendum (2026-08-21, [#391](https://github.com/juggernog20/OpenLaw/issues/391)) — the index carries the cursor's tie-break, not just its first column.** This decision pages on `(created_at, id)` and says why: the id breaks a same-instant tie, and uuidv7 is time-ordered, so that order is still the order things happened in. Four of the indexes behind those reads stopped one column short of the pair — `comments_entity_idx`, `documents_contract_idx`, `documents_folder_idx`, and `activity_log_entity_idx` all ended at `created_at`. Each answered the scope and most of the order and then left Postgres to sort the ties itself: cheap inside one thread, and the wrong shape for the read the index exists for.

  All four now end in `id`. This is not a new rule, it is the one the other two paged reads already keep — `activity_log_created_at_idx` for the audit log and `notifications_user_idx` for the bell were both written with the pair from the start. **A route that pages on `(created_at, id)` gets an index that ends in `id`**, and the next module reads that off the six sites rather than deriving it again.

  Migration `0064` does it. A column cannot be appended to an index in place, so each one is dropped and rebuilt, and the file opens its own transaction (TECH-006's 2026-08-21 addendum) because a rebuild that failed after its drop would leave the table with no index at all. The rebuild is plain rather than `CONCURRENTLY`: migrations run at container start (TECH-005), before the app answers `/readyz`, so the lock is held against no traffic of our own — and `CONCURRENTLY` cannot run inside the transaction that makes the drop-and-rebuild safe.
