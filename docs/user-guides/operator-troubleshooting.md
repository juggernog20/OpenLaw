# Troubleshoot a deployment

Identify the failing service or operation, apply a targeted correction, and verify the original action succeeds. Run commands from the installation directory with its established Compose project and file list.

## Start with the observed failure

Record the time, public origin, source/image identities, and affected action. If a particular Contract, Matter, or Document is involved, retain its reference and the displayed error. Keep raw configuration, tokens, and private file contents out of general support reports.

```bash
docker compose config --quiet
docker compose ps --all
docker compose logs --since=10m app worker
```

Read logs locally first: activity and provider errors may contain record titles or recipient details. A request line carries the path without its query string and no headers. An error line leaves out SQL parameters and masks URL passwords, credential-named query values and bearer tokens. That masking is a short fixed list, not a secret detector. Each activity line copies the stored entry in full. Share the relevant redacted excerpt, not an entire container log or expanded Compose configuration. Avoid starting a second project while diagnosing the first; it can look like a fresh installation because it has different volumes.

### Remove saved Advanced settings

An Administrator can save the instance address, upload limit, storage, document-service and MCP settings in **Settings → Advanced**. If a saved value stops the app, or blocks the sign-in needed to change it, set the key in the deployment environment. A non-empty value in `.env` pins that key and ignores the saved one; apply it with `docker compose up -d --no-build --pull never`. For a saved instance address this is the fix: removing the saved address alone leaves the app on `BASE_URL`, or on `http://localhost:3000` when `BASE_URL` is empty, and sign-in at the public address still fails. To remove one section's saved values from the installation directory:

```bash
docker compose run -T --rm --no-deps app node apps/api/dist/reset-advanced-settings.js instance
docker compose restart app worker
```

The command accepts `instance`, `uploads`, `storage`, `processing` or `mcp`. It removes only that section's saved values, prints none of them, and writes an Audit log entry. `run` starts a one-off container, so the command works while the app keeps restarting. Removing saved storage values does not move files. A Document in a bucket or container that only the saved values named stays unreadable until the deployment configures that store. Run the command only with the correct `OPENLAW_SECRET_KEY`. With a key that cannot open the saved settings, it still exits successfully and prints the same message, but it replaces the whole saved configuration with an empty one. That removes every section's saved values, not only the named section, and the correct key can no longer recover them. Check the start log first: if **No configured key opens these stored credentials** names `advanced_settings`, fix the key instead.

## Migration failures

Keep writes paused and take or preserve a [coherent backup](backup-and-restore.md). Read the exact migration error before changing anything. The app migrates at startup; the worker does not repair a failed migration.

If the app reports **This database cannot apply the migrations it is missing**, inspect the recorded journal and the hashes shipped with that exact image:

```bash
docker compose exec -T postgres psql -U openlaw -d openlaw -c 'select hash, created_at from drizzle.__drizzle_migrations order by created_at desc limit 5;'
docker compose run -T --rm --no-deps app node scripts/lint-migration-journal.mjs --hashes
```

Two known repairs are automatic when the app recognizes them: the `0049_contract_tasks` timestamp, and a database that recorded the earlier `0090_request_triage_assignee` migration. The app then logs `migrations: reconciled <migration>; continuing with pending migrations`. An unrecognized journal inconsistency needs a maintainer to reconcile the exact hash and expected timestamp against the backup and shipped migrations. Do not delete journal rows or mark an unapplied migration as complete to get past startup.

The `accounts.issuer` migration refuses rather than guessing an identity, and a refusal applies none of that migration. Read the app log for the case it names, and preserve the named account details. **Cannot resolve an issuer for accounts under provider(s)** means accounts still point at an identity provider the database no longer holds: re-register that provider under its original provider ID, or delete those account rows, after which those people re-link on their next sign-in through the provider. **Two accounts share one 1.7 identity** means one provider was registered twice and the same person signed in through both: keep the correct row and delete the duplicate. Correct what the log names, then start the target again. Do not rewrite sign-in identities by guesswork.

**Cannot migrate the intake form of Request types:** names each Request type whose intake questions include a Field with no Row on the destination type. The Field belongs to another module, is a Contract Overview attribute, or is a built-in question that has no Matter Row. The message appears inside the failed migration's SQL error. The pending migrations before this one stay applied, so do not start the old image against this database. Recover the pre-upgrade backup in a separate target, as described in [If the upgrade cannot be accepted](upgrade.md#if-the-upgrade-cannot-be-accepted). On that starting build, re-target each named Request type or remove those Fields from its questions. Then take a new coherent backup and repeat the upgrade.

If the target build cannot be accepted, use [backup-based recovery](upgrade.md#if-the-upgrade-cannot-be-accepted) in a separate target rather than booting an older image against a changed database.

## Email and stored credentials

Check whether `SMTP_URL` pins the environment configuration. If it does, the saved wizard relay is ignored. Supply a valid `SMTP_FROM` as well, recreate both app and worker, and verify a message in a controlled recipient's inbox. If the saved relay should apply, remove the environment override and recreate the containers.

If saved credentials appear unavailable after a deployment or restore, compare the intended `OPENLAW_SECRET_KEY` with the secret-store record without printing it. Both processes need the correct value. The app's start log names each stored column that no configured key opens, in a line that begins **No configured key opens these stored credentials**. The app and worker still start with a wrong key, and each of those values reads as empty. Saved **Settings → Advanced** values fall back to the environment or the defaults, including local storage and the `BASE_URL` or `http://localhost:3000` address. The Signing connector, AI connector and SSO provider lose their secrets, and device notifications stop. [Preserve and rotate encryption keys](deployment-configuration.md#preserve-and-rotate-encryption-keys) lists each symptom. In the app, a wrong key does not announce itself as a key problem: it reads a saved relay as absent, so the email state says email is unset and a test send fails with **The test email could not be sent. SMTP is not configured — save a relay first.** Saving a new relay at that point writes over a credential the retained key can still open. Restore the key before replacing saved credentials; an unrelated Contract remaining readable does not prove connector decryption works. Until the key is fixed, do not save in **Settings → Advanced** or run the saved-settings recovery command either. If the key is lost, pin `BASE_URL` and the storage variables in `.env`, then paste the credentials and save the Advanced values again, as described in [Preserve and rotate encryption keys](deployment-configuration.md#preserve-and-rotate-encryption-keys).

Use [deployment configuration](deployment-configuration.md) for key rotation, and [authentication and email](authentication-and-email.md) for the Administrator's controls. The production installation should not be using the development mail catcher.

## Storage and uploads

Check the write driver and every store referenced by older Documents. These settings come from `.env` or from **Settings → Advanced → Document storage**, where each field names its source. **System status** shows **Active storage**. **Test connection** on **Document storage** writes, reads and deletes a test object from the API only. The app and worker need the same configuration. Buckets and containers must already exist. Startup validates reader configuration even when another driver receives new uploads, but an unreachable endpoint can surface only when a file is read or written. A ready app does not establish storage access.

For local storage, retain the standard Compose path and check volume ownership for the image's unprivileged user. Do not use a broad recursive permission change on unrelated host directories. For object storage, check the endpoint, container/bucket, credentials, and network access. A change of write driver does not migrate earlier objects.

The app refuses an upload over its limit with a message such as **That file is over the 100 MB upload limit.** The limit comes from `MAX_UPLOAD_MB` or from **Settings → Advanced → File uploads**. A proxy with a smaller body limit refuses the upload first, with its own error. If an upload is too large, compare the app limit with the proxy body limit. Test a file below and above the intended ceiling after correcting the limits. If a Document is listed but cannot be downloaded, check its original store and bytes; do not delete the Document row to hide a missing file. Use [restore verification](backup-and-restore.md#verify-the-restored-instance).

## Worker and document processing

```bash
docker compose ps worker doc-engine
docker compose logs --since=10m worker doc-engine
```

The worker has no public port or HTTP readiness endpoint. Check that it is running, inspect its work result, and submit a new fictional Document to verify processing. It uses the app image with the worker command and must reach the same database and file stores.

As an Administrator, open **Settings → Advanced → System status** and select **Refresh**. Each API and worker process has a row. **No recent heartbeat** means the process sent no heartbeat in the last minute. **Restart required** means the process started with a different configuration from the saved one. A **Running** row does not prove that processing works.

An engine failure need not stop the API. Check the engine container, private endpoint, timeout settings, scratch-space limit, and memory limit. Scratch space counts against `DOC_ENGINE_MEM_LIMIT`. By default the engine runs two tools at once and holds eight more requests waiting. Past both, it answers 503 with `Retry-After`. The API and worker treat that answer as temporary and retry, so processing slows down rather than fails. Raise `DOC_ENGINE_MAX_CONCURRENT` and `DOC_ENGINE_MAX_QUEUED` only when the engine's CPU and memory limits allow it. Restore the dependency, then retry the failed operation through the app when offered or submit a new controlled input. Do not promise that every permanently failed processing record will retry merely because the engine restarted.

Confirm that the original file remains downloadable and inspect the Document's actual processing state. [Document reading and processing](document-previews.md) explains the reader-facing results. Do not publish the engine's port as a workaround for internal connectivity.

## External providers

For signing, check the saved environment/account, enabled state, outbound access, and the **Signing updates** mode. Polling needs outbound access only. Webhook also needs the public Connect callback. A green configuration badge is not a connection test, and a successful connection test is not a completed Envelope. Use [Signing connector recovery](configure-signing.md).

For Analysis, test the configured model and endpoint from Settings, then inspect an actual run. A failed test shows only the HTTP status, such as **The connection test failed. The provider refused the request with HTTP 401.** The app log then has the line `The AI provider refused the connection test.` with the provider's status and a short, redacted part of its reply. The API's probe can succeed while the worker cannot reach the provider or read the Document. Use [AI connector recovery](configure-analysis.md) and retain the run's Document Version and model when escalating.

Finish a diagnosis by repeating the failed action and checking its saved result, delivery, or downloaded bytes. Record the correction and the verified outcome with the deployment change.
