# MCP — grill plan and decision log

OpenLaw gets an MCP server so a person's AI agent can work in OpenLaw as that person. This document is the decision log of the grill that started on 2026-09-23. The evidence is in `MCP-RESEARCH.md` (sections 1 to 11). The glossary terms are already in `CONTEXT.md` under "MCP". The formal records are written; the list at the end says which.

Status of the grill: Rounds 1 to 5 are settled (Q1 to Q41). Round 6 (Q42 to Q46) is settled. The grill closed on 2026-09-23 and the records are written: DD-029, TECH-035, SET-014, DES-092, the DD-017, TECH-033, NOT-001 and NOT-005 addenda, FUTURE-FEATURES rows, CONTEXT.md terms, and M40 to M42 in the implementation plan. The mocks are `designs/mcp.pen`, frames MC1 to MC6.

## Where OpenLaw stands today

Facts from the codebase survey on 2026-09-23. Paths are relative to the repo root.

- No non-browser caller can authenticate today except the DocuSign webhook (HMAC) and the first-run setup token. There is no API key, bearer, service account, or bot user.
- better-auth is mounted with `admin`, `magicLink`, `sso`, `twoFactor` (`apps/api/src/auth/instance.ts:238`). Not enabled: `bearer`, `api-key`, `jwt`, `oauth-provider`, `mcp`.
- Three account types exist in code: `administrator`, `legal_team_member`, `business_user` (`packages/db/src/schema/auth.ts:24`). The guard chain resolves `request.user` as an `AuthenticatedUser` (`apps/api/src/auth/user.ts:23`), a Fastify-free shape the worker already reuses.
- Every access helper takes `(db, AuthenticatedUser)` and returns a SQL scope or an audience: `contractTeamScope`, `matterTeamScope`, `entityReachScope`, `documentRepositoryScope`, `commentAudience`, `portalContractScope`, `portalRecordScope`. An agent that resolves to an `AuthenticatedUser` inherits DD-014, DD-016 and DD-023 with no new code.
- The OpenAPI document holds 507 operations on 385 paths and declares no `securitySchemes`.
- Global search covers seven kinds with visibility enforced inside SQL (`apps/api/src/modules/search/routes.ts:544`).
- Activity rows carry `actor_id` (user or NULL for system) and a visibility tier. There is no "via" column. `recordActivity` is the single write path and emits the SIEM line (`apps/api/src/lib/activity.ts:143`).
- The audit log routes read the whole table with no record-level audience filter (`apps/api/src/modules/audit-log/routes.ts:525`). Fix before any audit tool exists.
- The event hub is one Postgres LISTEN with per-user scoped subscriptions (`apps/api/src/lib/event-hub.ts:53`).
- The origin check (TECH-033) covers `/api/v1/*` writes only; a `/mcp` mount is outside it. Rate limits exist only on sign-in.
- `BASE_URL` is origin-only, pinned by the environment (SET-013), exposed as `app.baseUrl`.
- Connectors are bespoke; the Integrations tab strip is a hard-coded array with one entry.
- The doc engine already extracts text from a Document Version (`apps/api/src/lib/doc-engine/`).
- Stack pins: zod 4.6, Fastify 5.12, better-auth 1.7.5, Node 24. SDK v2 needs zod 4.2+ and Fastify 5.2+. No upgrade blocks this.
- Free record numbers: DD-029, TECH-035, SET-014. Next milestone: M40.

## Settled decisions

### Identity and scope (Round 1)

| Q   | Decision                                                                                                                                                                                                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Q1  | **A person's agent works in OpenLaw as that person.** The agent is a new Client of an existing account. No bot identity, no service accounts, no org-owned keys. Unattended automation is parked in FUTURE-FEATURES with the trigger "a deployer asks".       |
| Q2  | **Vocabulary.** The feature is **MCP**. The credential is **API key** (the AI provider credential stays **Saved key**). A connected program is a **Client**. **Tool**, **Toolset**, **Tool register** as defined in `CONTEXT.md`.                             |
| Q3  | **Everyone from day one.** Legal Users and Business Users may both use MCP, subject to the per-group switches in Q12. No vendor documents portal-user MCP access (research section 9); OpenLaw is ahead of the field here and the Portal scopes make it free. |
| Q4  | **Same scopes exactly.** The MCP server cannot read or write anything the person could not in the UI. No extra restriction either, except defaults (a comment tool defaults to the most restrictive tier the person may use).                                 |

| Q7  | **Curated register plus guidance tools.** About 30 hand-written task-shaped Tools in Toolsets, plus a `guide` Toolset (docs search and read, whoami, vocabulary, forms). No generation from OpenAPI. Meta-tools over the API are a recorded later step.       |
| Q8  | Resolved by Q9.                                                                                                                                                                                                                                               |

### Authentication and reachability (Rounds 2 to 4)

| Q   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Q9  | **OAuth is the main path, API keys the power-user path.** Two Administrator switches, both off by default: "Allow API keys" (works on a LAN) and "Allow OAuth Clients" (chat clients; needs public reachability). Turning OAuth on names the exposed paths (`/mcp`, `/.well-known/oauth-*`, the consent page) and links the deployment note. Build order: keys and read tools first, then OAuth; both are v1 scope.                                                                                                               |

| Q12 | **Per-group switches, and Administrator approval of API keys.** The MCP section shows one row per group (Legal Users, Business Users) with "OAuth Clients" and "API keys" toggles. | Q13 | **Ceiling plus per-grant choice.** The organization sets a Toolset ceiling and an org-wide read-only switch. Read-only always wins.                                                                                                                                                                                                                                                                                      |
| Q14 | **Nothing pre-selected** on the key request form or the consent page. The person picks each Toolset and the scope.                                                                                                                                                                                                                                                                                                                                                                                                                |
| Q21 | **Approval flow.** A person fills the Client name, Toolsets and scope, and may add a note; the expiry is a fact from the organization key lifetime (Q46). | Q22 | **OAuth grants need no per-grant approval.** The Allowed Clients list, the group toggle and the ceiling are the Administrator's controls. Every grant is visible and revocable by an Administrator.                                                                                                                                                                                                                                                                                                                               |
| Q23 | **Key lifetime.** Administrator-set organization lifetime, default 90 days, hard cap 365. The request form shows it as a fact (Q46). Renewal is a new request.                                                                                                                                                                                                                                                                                                                                                                    |
| Q24 | **Rate limit and result size.** Calls-per-hour per credential, org default 600, configured in Advanced settings. | Q31 | **API key transport.** Accept the key as `Authorization: Bearer` and as `x-api-key`. Keys serve Claude Code, Copilot Studio, the Claude and OpenAI developer APIs, and scripts. ChatGPT users always take the OAuth path (ChatGPT has no place for a key); the guides say so.                                                                                                                                                                                                                                                     |
| Q33 | **Reachability guard warns, does not refuse.** When the OAuth switch is turned on and `BASE_URL` resolves to a private address or has no IPv4 record (Claude rejects both), OpenLaw warns with the failed checks and lets the Administrator proceed, since a proxy may front the API.                                                                                                                                                                                                                                             |
| Q34 | **Microsoft routes supported: Copilot Studio and Microsoft 365 declarative agents.** Both use the registered client from Q28. The registered client needs three callbacks: the pasted Copilot Studio `global.consent.azure-apim.net` URL, `https://teams.microsoft.com/api/platform/v1.0/oAuthRedirect`, and `https://vscode.dev/redirect` (Agents Toolkit tool fetch). The admin-center BYO registry, still in preview, gets a note only.                                                                                        |

Server facts the records must carry (research section 10): serve both protocol eras on one Streamable HTTP endpoint (Claude already speaks 2026-07-28; ChatGPT and Microsoft still send `initialize`); advertise `client_id_metadata_document_supported: true` and `none` in `token_endpoint_auth_methods_supported` or Claude falls back to DCR; advertise PKCE S256 and `authorization_response_iss_parameter_supported: true` with `iss` in responses or ChatGPT refuses; publish protected resource metadata at both well-known forms and `WWW-Authenticate` on 401 and 403; allowlist redirects `https://claude.ai/api/mcp/auth_callback`, `http://localhost/callback` and `http://127.0.0.1/callback` (any port), `https://chatgpt.com/connector_platform_oauth_redirect`, `https://chatgpt.com/connector/oauth/{callback_id}`, plus the Microsoft three above; public IPv4 HTTPS host with no cross-host redirects; deployer allowlists Anthropic `160.79.104.0/21`, OpenAI `chatgpt-connectors.json`, and the regional `AzureConnectors` plus `PowerPlatformPlex` service tags; tool calls under 30 seconds.
