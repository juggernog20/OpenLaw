## Independent operator acceptance

A different agent from the author ran the five scenarios against the same candidate `6a8873dbda333fd9992eb77525d4bfa3f47af20d`, on four fresh projects of its own: `rev-install` (app 43360, mail 48460, MinIO 48461, Azurite 48462, local TLS 43372), `rev-upgrade` (app 43364, mail 48463) built from the earlier development revision `d1d098ba9f4ba6557a542857d530446b76b1847c`, `rev-restore` (app 43367, mail 48470) and `rev-recovery` (app 43373). Every project used its own generated keys and its own fictional people: Avery Morgan and Rowan Operator on the installation, Morgan Baseline and Rowan Reader on the upgrade fixture, Sam External on the separate database. The reviewer's `independent-*.json` records hold the real action times, the article hashes tested, the method of each step and the failed attempts. Keys, relay credentials and mail links stay outside the repository.

The installation followed the article literally, from `git clone` of the public repository to the first Administrator. From the first prerequisite command to `/readyz` 200 took 32 seconds on that host with a warm image cache, and about four minutes to the end of the article's working-installation checks, including one failed attempt and the reviewer's own gaps between phases. A `--no-cache` rebuild of both images took a further 32 seconds. That is well inside M34's under-an-hour goal on this host, and it is not a claim about a slower host, a cold dependency store, or the time to arrange DNS, a public certificate and a proxy.

Configuration was exercised with real files and requests: local, S3-compatible and Azure Blob storage in turn, with every earlier store still readable after each switch; a 1 MB ceiling refusing a 1,100,000-byte upload; a local Caddy origin carrying sign-in, uploads, an unbuffered event stream and an invitation, with a foreign `Origin` refused; a separate Postgres 16 service selected and then released without disturbing the original database; the environment SMTP override winning over the saved relay and giving it back when removed; and a full key rotation, including the boot line `Stored credentials resealed under the key in use: smtp_url (1)` and real delivery after each recreation.

The upgrade started from a populated earlier build holding three Contracts, one of them Confidential, a Matter, two Documents with an original and a later Version each, an encrypted relay and an activated Contributor with membership on one Contract. After the upgrade every record, every Version hash, the Contributor's reach and the saved relay's actual delivery survived, and a new upload processed. The coherent backup was taken at the point the upgrade article calls for it, restored into a separate empty target, and verified there in full; the pre-upgrade backup was separately restored onto the build that wrote it, which is the recovery the upgrade article describes. Nothing pointed an older image at a migrated database.

Diagnostics were induced one at a time and reversed: a short `AUTH_SECRET`, an unresolvable database endpoint, a database stopped under a running app, an unreachable retained S3 reader, a stopped worker, an unreachable document engine, and a controlled journal fault that produced the stranded-journal refusal and was undone from the exact recorded row. Both read-only journal commands ran against the refusing installation and named the migration. Signing and Analysis diagnostics were not exercised, because that provider access is still blocked.

### Corrections from the walkthrough

Three more corrections came out of the runs and were then re-checked against the corrected bytes, recorded in `independent-corrections-confirmed.json`.

`backup-and-restore` recorded the wrong provenance during an upgrade. Following the two articles in their own order puts the checkout on the target before the backup is taken, so `git rev-parse HEAD` wrote the target revision into `app-source.txt` while `images.json` correctly named the earlier images that had written the data. Step 3 now says to take the running build's identity from `images.json`.

`operator-troubleshooting` gained the symptom a wrong credential key actually produces. The app then reads a saved relay as absent: the email state says email is unset and a test send fails with "The test email could not be sent. SMTP is not configured — save a relay first." An operator following that message would overwrite a credential the retained key can still open. The same article's port row now says that a failed bind leaves the app and worker containers removed, which is what happened on both projects where it was tried.

### Failed attempts

Ten steps across the reviewer's records are failures, kept with their original text and linked to the record that superseded them. Most were faults in the reviewer's own checkers rather than observations about the product: a wait for a control named "Send invitation" when the wizard's control is "Send invite"; an `EventSource.onmessage` handler that cannot see named SSE frames; a sign-in over the direct port while `BASE_URL` still pointed at the proxy origin; a second sign-in while a session already existed; `confidential` where the API takes `isConfidential`; a `/contracts/:number/members` route that does not exist; a re-invitation of an already activated account; and a version-upload response read as if its `versions[0]` were the new Version, which produced a byte-mismatch scare that both files then disproved by hashing. One wrong-key check crashed on a readiness race straight after a container recreate and was re-run.
